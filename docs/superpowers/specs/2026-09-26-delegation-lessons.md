# Delegation rework journal and lessons

User approved implementation of a local, per-assignment rework journal and periodic coordinator revision of task-delegation rules. Preserve existing uncommitted learned-quality routing and stats work. The journal preserves access, forced effort, activation and sandbox policy. The later user-approved quality assessment extension below changes ranking independently of operational rework.

## Behavior

Record append-only outcome events linked to task/assignment, including clean successes. Automatic context contains original deliverable/features/acceptance/checks, actual runtime/effort, workspace/source/prepared-change and worker-change references, declared check results, and the version/IDs/content of applicable lessons captured before execution. Reuse existing private evidence references; never copy credentials or raw model logs into Git. Coordinator supplies cause, severity, summary, prevention, and verifiable evidence when accepting a result requiring corrections. Multiple dispositions/attempts remain one case; later incorporation does not erase earlier rework. Older outcomes without structured attribution remain unknown.

Causes: worker_error, brief_gap, context_gap, requirements_changed, integration, environment, mixed, unknown. Severity: minor, major, redo, unknown. Unknown is an explicit valid finding. Keep feedback and rules in private per-project local state, including generated DELEGATION_LESSONS.md; no automatic edits of project AGENTS.md or source based on model output.

A review is due after 10 distinct newly reviewed/updated cases since the last review, or 3 distinct rework cases with the same task kind and non-unknown cause. Repeated events for one assignment cannot meet either threshold. The coordinator receives a review reminder at a completed-task boundary and subsequent session/prompt/policy resolution. The application does not call a model or execute instructions itself. Coordinator reads the review bundle, checks evidence, submits a bounded full replacement ruleset or a justified no-change review. No repeated Stop veto for lessons.

Rules carry id, feature match, natural-language condition, concrete action, and supporting case IDs. Maximum 20 active rules. Apply matching rules before subsequent delegation and retain exact version on assignments. Rules are advisory task-planning guidance subordinate to user instructions, access/effort settings and sandbox requirements. Reviewer evaluates repetition and comparable kind/effort cohorts including successes; descriptive counts never establish causal improvement.

## Shared Python contract (stdlib only)

New module codex_deepseek_team.lessons, independent of coordination/worker to avoid cycles; LessonError(ValueError). All root arguments are project Path. Private state under Path.home()/.local/state/codex-deepseek/lessons/<sha256 resolved project path first 24>/; SQLite transactional append-only outcome/review history and generated Markdown from canonical versioned rules. Read-only empty-state queries create no files. Lock/atomic handling must preserve concurrent events and reject symlink files. Generated Markdown can be recovered from canonical rules.

- validate_rework(value: dict | None) -> dict | None: reject wrong types/unknown keys; when supplied requires cause,severity,summary,prevention, all bounded nonempty strings. Evidence stays the required outer outcome evidence.
- record_outcome(root, *, task_id, assignment_id, disposition, evidence, context, rework=None) -> dict: case_id is task_id + '/' + assignment_id. disposition is incorporated/reproduced/needs-rework/rejected. JSON context supplied by integration. Exact replay idempotent. Event has seq,case_id,at,disposition,evidence,context,rework. No quality inference from cause.
- journal(root) -> list[dict]: chronological events, stable sequence.
- snapshot(root, features=None) -> dict: {version:int, rule_ids:[str], rules:[dict]}; if features None all active rules; otherwise exact match supplied when fields. Empty/missing feature cannot match a constrained rule. No global policy mutation.
- status(root) -> dict: version, rules_file, review_due, due_reasons, cases_since_review, through_event, counts (cases,clean,rework,rejected,unknown_attribution), cohorts (kind,effort,version,cases,clean,rework,rejected), causes/severities. Any case with historical needs-rework stays rework; rejection separately remains visible.
- review_bundle(root) -> dict: status fields plus expected_version, reviewed_through, cases (consolidated events by case, including context/evidence), rules. Include enough past evidence for existing active rules and all cases for first release.
- apply_review(root, payload:dict) -> dict: exact {expected_version,through_event,summary,rules}; optimistic version check; through_event must be a valid snapshot sequence, cannot go backwards or acknowledge concurrent newer events. Rules exact {id,when,condition,action,evidence}; when allowed scalar exact keys kind/domain/operation/runtime/effort (normalize medium to high), no extra keys; evidence nonempty list of known case_ids at or before through_event. Validate everything before writes. Max20 rules; bounded text. Version increases even for explicit no-change review; immutable old reviews. Only acknowledges through_event. Generates Markdown with evidence references. Returns status.
- render_guidance(root, features=None) -> str: concise advisory rules and due reminder with actual lessons CLI commands. Empty state returns empty string. No writes, no execution.

## CLI and integration contract

`deepseek-team lessons status [--json]`, `lessons journal [--json]`, `lessons review [--json]` read state; all accept --path. `lessons review --apply FILE` (or - stdin) accepts shared review payload, validates references/version and updates canonical state/Markdown. `lessons rules [--json]` prints current rules/Markdown. Read commands output human-readable forms by default, structured JSON with --json.

`coordination use --rework-json FILE|-` attaches structured reason to existing --disposition/--evidence; compatible omission becomes unknown for rework/rejection. Preserve old disposition history and routing behavior. Capture applicable lessons before assignment starts, not at outcome. Include coordinator policy/config instructions and both runtime lifecycle prompts, and surface due review on normal task completion without preventing user stop/off/plan mode. Static managed instructions explain recording and periodic review. Worker never revises host rules. Snapshot references source HEAD/prepared changes/checks and prompt digest/reference when available; missing old context remains explicitly unknown. Integration uses a durable task outbox for journal replay after interruptions, with one-way lock order coordination then lessons. Replaying a running assignment retains its execution snapshot; resumed failed attempts retain older snapshots. Structured rework attached to incorporation must not count as a clean result.

## User steering: canonical bootstrap correction workflow

This workflow belongs to reusable DeepSeek Team bootstrap/effective instructions and both runtime lifecycle contexts, not a standalone project AGENTS addendum. Minor bounded corrections may be performed by the coordinator and recorded. Substantive corrections normally return to DeepSeek with an explicit routed assignment containing original assignment link, concrete defect/evidence, missing context and executable acceptance checks. Inspect actual output before explicit continuation; no automatic retries, off overrides, access widening or sandbox bypass. Architecture/security decisions and final integration/verification remain coordinator-owned. Saved policies remain authoritative. Existing project-owned prose outside generated blocks is preserved on refresh.

Correction size is distinct from quality severity: a one-line security/correctness defect may be serious; cosmetic changes can preserve full quality credit. Do not take over substantive work merely after the first attempt. A blocked worker correction requires an explicit explanation and policy-compliant next step, not a silent bypass.

## User steering: explicit graded quality

Operational disposition (incorporated/reproduced/needs-rework/rejected), rework cause/severity and worker quality are distinct. Add optional `quality` to routing observations and `coordination.use_result`, and `coordination use --quality-json FILE|-`. An assessment is exactly `{grade, attribution, evidence}` with bounded nonempty evidence (4000 characters maximum). Grades: `met`=1.0, `minor_gaps`=0.8, `major_gaps`=0.3, `unusable`=0.0, `unassessable`=null. Attribution: `worker`, `shared`, `coordinator`, `environment`, `unknown`. Only worker/shared with a assessable grade supplies a quality score; shared evidence must name the worker-attributable gap against the supplied requirements, without guessing a numerical responsibility share. Infrastructure/cancelled/unknown outcomes stay neutral regardless of assessment. These are declared rubric weights, not measured probabilities or work-share percentages.

`met` includes fully satisfied supplied requirements with cosmetic/preference edits. `minor_gaps` means a bounded actual missed requirement with usable main result; `major_gaps` means a substantial supplied requirement failed; `unusable` means the main requested result failed. Missing context/brief or changed requirements alone is neutral for worker quality. A low editing cost does not justify `met` for a serious defect. Coordinator supplies assessment and evidence; workers do not self-grade. Omitted quality remains legacy binary accepted=1/rework=0/rejected=0 for compatibility, explicitly identified in statistics; do not guess historical causes or rewrite old observations.

One assignment remains one case. Preserve raw operational first-failure counts/history. For quality, explicit assessments replace that case's legacy inference; if several explicit assessments exist, retain the lowest scored worker assessment (earliest tie), so later incorporation or neutral attribution cannot launder a known worker defect. If explicit assessments exist but none are scored, the case is neutral. Without any explicit assessment preserve existing first-labelled-failure behavior. Ordinary incorporation without quality never erases an assessment. Evidence-backed grading of older binary cases is allowed by appending an explicit assessment, not editing history. Preserve execution identity, evidence age, minimum support and unknown/new-category immediate delegation behavior.

Weighted quality uses fractional success/failure mass (score and 1-score) with the existing aging, similarity and support safeguards. Table distinguishes explicit, legacy and neutral quality cases and raw rework counts. Label ranking as rubric-based quality, not clean-first-pass probability. Explicit cosmetic/minor-gap/neutral feedback must not trigger the hard failure cooldown; scored major_gaps/unusable count as substantive failures under existing one-rejection/three-reworks rules. Existing active cooldowns expire normally; do not clear pauses by rewriting state. Preserve chronological evaluation semantics and costs independent of quality.

Coordination validates assessment before state changes, includes assessment in idempotence/outbox fingerprints and the lessons context, replays durable routing/lessons feedback without duplicates. CLI accepts at most one stdin JSON source when both feedback flags are supplied. Bootstrap teaches both feedback flags and the rubric, so current and newly attached projects receive the same workflow even before any lessons exist. Tests cover cosmetic rework full credit, actual minor gap fractional credit, brief/context gaps neutral, serious one-line error penalty, unchanged legacy behavior, earlier explicit failure survives later acceptance, invalid assessment leaves all state unchanged, both runtime hook/bootstrap contexts and actual CLI roundtrip.

### Review clarification: identity across context versions
Graded quality belongs to (origin, case_id, action, runtime, model, canonical effort); context_version is provenance, never a second quality case. Exact-context forecast matching still requires its original context_version, and cost identity/semantics remain unchanged. A later explicit grade under another context_version must reach the same assignment's earlier forecast-context evidence and retrospective evaluation target, only after that event arrives. Raw operation counts remain failure-dominant for the same evaluation case. Cooldown family still has its existing context identity, but qualifying an assignment uses all its same-runtime/model/effort quality assessments, not just those in the family's context. No duplicate support, no future leakage or observed history rewrite.
