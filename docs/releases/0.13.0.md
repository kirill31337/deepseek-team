# DeepSeek Team 0.13.0

## English

0.13.0 adds Qwen inside the DeepSeek Harness (DSH) as a third coordinator runtime,
with a package-native DeepSeek worker loop, and makes the DeepSeek credential
location configurable for services whose `HOME` is not the interactive user's home.

### Qwen (DSH) coordinator runtime

- `qwen` is accepted wherever a coordinator runtime is selected: `setup --runtime`,
  `reset --runtime`, `init`/`detach --coordinator`, `hooks install|status|remove`
  and `hooks refresh --runtime`, `doctor --runtime`, `update --runtime`,
  `config show --instructions --runtime` and `coordinator-hook --runtime`. `both`
  still means Codex plus Claude Code; the new value `all` selects all three.
- Workers of a Qwen coordinator use a package-native DeepSeek loop:
  `worker --runtime qwen` runs the shipped, dependency-free `native_worker.py`
  (`read` for report-only work, `full` inside a managed copy) directly against the
  DeepSeek Responses API, inside the same mandatory Bubblewrap/AppArmor boundary
  and provider relay as the CLI harnesses. A Qwen + DeepSeek setup therefore needs
  **no Codex and no Claude Code CLI**.
- Detection stays explicit and fail-closed: an existing DSH profile under
  `$DSH_HOME/profiles` (default `~/.dsh`) or the profile named by
  `DEEPSEEK_TEAM_DSH_PROFILE` is enough for `--runtime auto` to include `qwen`;
  an ambiguous or inaccessible profile is diagnosed, never guessed, and a missing
  profile makes `setup --runtime qwen` explain what to install or set.
- The bridge plugin ships as package data
  (`codex_deepseek_team/data/dsh-bridge/`, dependency-free ESM). Registration
  writes exactly one owned, marker-delimited `insert:` row into the active
  profile's `cordis.patch.yml`, pointing at the absolute bridge path and the
  absolute `deepseek-team` entrypoint. No pnpm run, network access or
  `package.json` change is involved; every byte outside the owned block is
  preserved, the write is atomic with a concurrent-change check, symlinked or
  non-regular patch files are refused, and a foreign row reusing the plugin id is
  reported instead of adopted. `reset --runtime qwen` removes only the owned block.
- The bridge binds root agents only and translates DSH events into
  `deepseek-team coordinator-hook --runtime qwen`: `agent/created` → `SessionStart`,
  a fresh user message in `agent/pre-step` → `UserPromptSubmit`,
  `tools/pre-execute` → `PreToolUse`, `tools/post-execute` → the early-planning
  nudge, and `agent/turn-stopping` → `Stop`. A failed or timed-out planning or
  authorization call denies the action instead of letting it through. Native DSH
  subagents, forks and team members never open or complete the coordination
  ledger, and dispatching them still requires the
  `[deepseek-team:TASK_ID:DELIVERABLE_ID]` binding.
- The Qwen hook protocol is the Claude-compatible JSON protocol, so the same
  gates, coordinator contexts, upgrade notices, receipts and diagnostics apply,
  and DSH tool names (`edit`, `write`, `terminal_send`, `read_image`, `lsp` and
  the native dispatch tools) are classified like their Codex/Claude equivalents.
- Qwen reads `AGENTS.md` natively, so it shares that one managed block with Codex:
  a multi-runtime selection renders the shared file once, and each session's hooks
  still inject the complete current policy for their own runtime, so a stale
  snapshot in the shared file never governs a session.
- The automatic first-use CLI refresh deliberately leaves the DSH profile alone:
  installing, migrating or repairing the bridge row stays an explicit
  `hooks install|refresh --runtime qwen` action, and
  `hooks status --runtime qwen` reports whether the bridge is present.
- See the [DSH guide](../DSH.md) for the event contract, the ownership rules and the
  coverage limits. New suites cover the runtime: `tests/test_qwen_cli.py`,
  `tests/test_qwen_hooks.py`, `tests/test_qwen_bridge.py` and the bridge's own
  `tests/dsh_bridge/`.

What this enables for DSH users: a Qwen coordinator session gets the same
delegation contract, plan/ledger gates, workspace isolation, review and
finalization flow and worker sandbox as Codex and Claude Code, while the
DeepSeek workers themselves come from this package instead of an external CLI.

### Credential location for services

- `DEEPSEEK_TEAM_CREDENTIAL_FILE` names the absolute path of the key file itself
  (not a directory) and fully replaces the `~/.config/codex-deepseek/api-key`
  default for reads, for `auth set` and for `auth remove`, so a key is never
  written to one location and read from another.
- The resolution order stays `DEEPSEEK_API_KEY` first, then the file named by the
  override, then the home default. A `DEEPSEEK_API_KEY` that is present but empty
  or malformed is an error (exit code `78`) and is never replaced by a file. An
  empty or unset `DEEPSEEK_TEAM_CREDENTIAL_FILE` selects the home default; a
  non-empty value that is relative, contains `..` or has no final component is
  rejected before anything is opened.
- Validation is enforced on opened descriptors and fails closed: the parent
  directory must be owned by the effective user with mode `700`; the file must be
  a regular file owned by that user with mode `600` holding one nonempty
  printable-ASCII value of at most 4096 bytes; both are opened with `O_NOFOLLOW`,
  so a symlinked path is rejected instead of followed and a FIFO or device never
  blocks or absorbs a read. With the override set, an unsafe, foreign-owned,
  shared or unreadable location raises a configuration error naming the path and
  the reason, never the stored value, and **no fallback** to the home default
  happens. A missing file inside a valid directory means "no key configured"
  (`auth status` exits `78`) and is likewise not replaced by the home key.
- This fixes saved keys becoming invisible when a service runs under a different
  `HOME` than the user who stored the key, and gives services, containers and CI
  a stable path that does not depend on `HOME`.
- `auth status` now reports the effective source and the searched locations - the
  override path and the effective `HOME` - and never the key; credential-absent
  worker errors name the searched locations too and keep the workspace.
- The worker environment remains an allowlist: `DEEPSEEK_TEAM_CREDENTIAL_FILE` is
  never forwarded into the sandbox, the parent's `DEEPSEEK_API_KEY` is never
  inherited, and each launch receives only the credential resolved for it.
- The rules and a systemd example are documented in
  [hardening](../HARDENING.md) (Russian: [docs/HARDENING.ru.md](../HARDENING.ru.md)).

### Other changes

- A cancellation that was completed before this release - terminal, cleaned,
  with no execution, whose task baseline has since moved to a newer source base -
  can now be finalized and cleaned with a narrow read-only replay instead of
  failing as conflicting history. The replay corroborates exactly the persisted
  publication and never executes a worker, captures changes or reads a
  credential; recorded execution data, a foreign project or task, a replacement
  workspace or any disagreement with the saved decision is still refused with the
  history preserved.
- Upgrade notices and their receipts now cover the DSH runtime as well, so a Qwen
  session receives the same post-upgrade guidance as Codex and Claude Code, with
  DSH-specific wording (reload the profile or restart DSH, then start a new
  session) instead of `/hooks` trust instructions.

### Upgrade

From an installation older than 0.13.0, upgrade through the manager you already
use:

```bash
pipx upgrade deepseek-team
# or: uv tool upgrade deepseek-team
# or, inside an activated venv: python -m pip install --upgrade deepseek-team

deepseek-team hooks refresh --runtime auto --notify --json
```

Existing settings, saved credentials, attached projects and coordinator
integrations are preserved; the new credential variable is optional and changes
nothing while it is unset. Codex and Claude Code users need nothing beyond the
usual refresh, then a new session. DSH users who already own a bridge row can run
`deepseek-team hooks refresh --runtime qwen` to migrate the earlier row shape,
then reload the DSH profile (or restart DSH) and start a new session. From 0.12.0
onward `deepseek-team update --runtime all` performs the same upgrade and refresh.

### Limitations

- The bridge plugin is JavaScript and its own suite runs under Node; without Node
  (or `DEEPSEEK_TEAM_NODE`) that test is skipped, while the Python hook protocol
  stays covered by `tests/test_qwen_hooks.py`. The package can neither inspect nor
  grant the native DSH profile load: reload the profile or restart DSH and start a
  new session yourself.
- Qwen workers are DeepSeek workers like the others: they need Linux with a
  working Bubblewrap OS sandbox (and the AppArmor prerequisites where the
  distribution requires them) before any credential is read, and that boundary
  cannot be turned off. DSH itself is not sandboxed by this package, and hook
  coverage is per event and never universal.
- Offline fixtures verify local behavior; only an explicitly authorized live
  provider check exercises real inference. Native Windows and macOS remain
  unsupported.

## Русский

0.13.0 добавляет Qwen внутри DeepSeek Harness (DSH) как третий рантайм координатора
с нативным циклом DeepSeek-воркера из пакета и делает расположение ключа DeepSeek
настраиваемым для служб, у которых `HOME` не совпадает с домашним каталогом
интерактивного пользователя.

### Рантайм координатора Qwen (DSH)

- `qwen` принимается везде, где выбирается рантайм координатора: `setup --runtime`,
  `reset --runtime`, `init`/`detach --coordinator`, `hooks install|status|remove`
  и `hooks refresh --runtime`, `doctor --runtime`, `update --runtime`,
  `config show --instructions --runtime` и `coordinator-hook --runtime`. Значение
  `both` по-прежнему означает Codex и Claude Code, а новое `all` выбирает все три.
- Воркеры координатора Qwen используют нативный цикл DeepSeek из пакета:
  `worker --runtime qwen` запускает поставляемый вместе с пакетом
  `native_worker.py` без внешних зависимостей (режим `read` для работы только с
  отчётом, `full` внутри управляемой копии) напрямую к DeepSeek Responses API,
  внутри той же обязательной границы Bubblewrap/AppArmor и того же релея
  провайдера, что и CLI-обвязки. Поэтому связке Qwen + DeepSeek **не нужны ни
  Codex CLI, ни Claude Code CLI**.
- Обнаружение остаётся явным и отказным при сомнении: существующего профиля DSH в
  `$DSH_HOME/profiles` (по умолчанию `~/.dsh`) или профиля из
  `DEEPSEEK_TEAM_DSH_PROFILE` достаточно, чтобы `--runtime auto` включил `qwen`;
  неоднозначный или недоступный профиль диагностируется, но не угадывается, а при
  отсутствии профиля `setup --runtime qwen` объясняет, что установить или задать.
- Bridge-плагин поставляется как данные пакета
  (`codex_deepseek_team/data/dsh-bridge/`, ESM без зависимостей). Регистрация
  записывает ровно одну принадлежащую пакету строку `insert:` с маркерами в
  `cordis.patch.yml` активного профиля, указывая абсолютный путь к bridge и
  абсолютный путь к точке входа `deepseek-team`. Запуск pnpm, сетевой доступ и
  изменение `package.json` не нужны; все байты вне принадлежащего блока
  сохраняются, запись атомарна и проверяет конкурентное изменение, символические
  ссылки и нерегулярные файлы патча отклоняются, а чужая строка с тем же id
  плагина только диагностируется и не присваивается. `reset --runtime qwen`
  удаляет только принадлежащий блок.
- Bridge подключает только корневых агентов и переводит события DSH в
  `deepseek-team coordinator-hook --runtime qwen`: `agent/created` → `SessionStart`,
  новое сообщение пользователя в `agent/pre-step` → `UserPromptSubmit`,
  `tools/pre-execute` → `PreToolUse`, `tools/post-execute` → подсказка раннего
  планирования, `agent/turn-stopping` → `Stop`. Неудачный или просроченный вызов
  планирования и авторизации отклоняет действие, а не пропускает его. Нативные
  субагенты, форки и участники команды DSH никогда не открывают и не закрывают
  журнал координации, а их запуск по-прежнему требует привязки
  `[deepseek-team:TASK_ID:DELIVERABLE_ID]`.
- Протокол хуков Qwen — совместимый с Claude JSON-протокол, поэтому действуют те
  же шлюзы, контексты координатора, уведомления об обновлении, квитанции и
  диагностика, а имена инструментов DSH (`edit`, `write`, `terminal_send`,
  `read_image`, `lsp` и инструменты нативного запуска) классифицируются так же,
  как их аналоги в Codex/Claude.
- Qwen читает `AGENTS.md` нативно и потому разделяет этот единственный
  управляемый блок с Codex: при выборе нескольких рантаймов общий файл
  отрисовывается один раз, а хуки каждой сессии всё равно передают полную текущую
  политику своего рантайма, поэтому устаревший снимок в общем файле никогда не
  управляет сессией.
- Автоматический refresh при первом использовании CLI намеренно не трогает профиль
  DSH: установка, миграция и починка строки bridge остаются явным действием
  `hooks install|refresh --runtime qwen`, а `hooks status --runtime qwen` сообщает,
  присутствует ли bridge.
- См. [руководство по DSH](../DSH.ru.md) с контрактом событий, правилами владения и
  границами покрытия. Новые наборы тестов: `tests/test_qwen_cli.py`,
  `tests/test_qwen_hooks.py`, `tests/test_qwen_bridge.py` и собственные тесты
  bridge в `tests/dsh_bridge/`.

Что это даёт пользователям DSH: сессия координатора Qwen получает тот же контракт
делегирования, те же шлюзы плана и журнала, изоляцию рабочих копий, процесс
проверки и финализации и ту же песочницу воркера, что и Codex с Claude Code, а
сами DeepSeek-воркеры берутся из этого пакета, а не из внешнего CLI.

### Расположение ключа для служб

- `DEEPSEEK_TEAM_CREDENTIAL_FILE` задаёт абсолютный путь именно к файлу ключа (а не
  к каталогу) и полностью заменяет путь по умолчанию
  `~/.config/codex-deepseek/api-key` при чтении, при `auth set` и при
  `auth remove`, поэтому ключ не может быть записан в одно место, а прочитан из
  другого.
- Порядок выбора остаётся прежним: сначала `DEEPSEEK_API_KEY`, затем файл из
  переменной, затем путь в домашнем каталоге. `DEEPSEEK_API_KEY`, заданная пустой
  или с недопустимым значением, даёт ошибку (код `78`) и никогда не подменяется
  файлом. Пустая или незаданная `DEEPSEEK_TEAM_CREDENTIAL_FILE` выбирает путь в
  домашнем каталоге; непустое значение с относительным путём, `..` или без имени
  файла отклоняется до открытия чего-либо.
- Проверки выполняются по уже открытым дескрипторам и при любом сомнении
  отклоняют операцию: каталог должен принадлежать действующему пользователю с
  режимом `700`; файл должен быть обычным файлом того же пользователя с режимом
  `600` и содержать одно непустое печатаемое ASCII-значение до 4096 байт; оба
  открываются с `O_NOFOLLOW`, поэтому символическая ссылка отклоняется, а не
  раскрывается, а fifo или устройство не блокируют и не поглощают чтение. Если
  переменная задана, небезопасное, чужое, общедоступное или недоступное
  расположение даёт ошибку с путём и причиной, но без значения ключа, и **никакого
  перехода** к пути в домашнем каталоге не происходит. Отсутствие файла в корректном
  каталоге означает «ключ не настроен» (`auth status` возвращает `78`) и тоже не
  заменяется ключом из домашнего каталога.
- Это исправляет ситуацию, когда сохранённый ключ становился невидимым, если служба
  работает под другим `HOME`, чем пользователь, сохранивший ключ, и даёт службам,
  контейнерам и CI постоянный путь, не зависящий от `HOME`.
- `auth status` теперь сообщает действующий источник и места поиска — путь из
  переменной и действующий `HOME` — и никогда сам ключ; ошибки об отсутствии
  учётных данных у воркера тоже называют места поиска и сохраняют рабочую копию.
- Окружение воркера остаётся белым списком: `DEEPSEEK_TEAM_CREDENTIAL_FILE` не
  передаётся в песочницу, `DEEPSEEK_API_KEY` родительского процесса не
  наследуется, а каждый запуск получает только ключ, выбранный для него.
- Правила и пример для systemd описаны в [docs/HARDENING.ru.md](../HARDENING.ru.md)
  (английская версия: [docs/HARDENING.md](../HARDENING.md)).

### Прочие изменения

- Отмена, завершённая до этого выпуска — терминальная, очищенная, без выполнения,
  чья базовая точка задачи с тех пор сместилась на более новый исходный коммит, —
  теперь финализируется и очищается узким воспроизведением только для чтения, а не
  завершается ошибкой конфликтующей истории. Воспроизведение подтверждает ровно
  сохранённую публикацию и никогда не запускает воркер, не собирает изменения и не
  читает учётные данные; записанные данные выполнения, чужой проект или задача,
  подменённая рабочая копия и любое расхождение с сохранённым решением по-прежнему
  отклоняются с сохранением истории.
- Уведомления об обновлении и их квитанции теперь охватывают и рантайм DSH, поэтому
  сессия Qwen получает ту же подсказку после обновления, что и Codex с Claude Code,
  но с формулировкой для DSH (перезагрузите профиль или перезапустите DSH и начните
  новую сессию) вместо инструкций о доверии в `/hooks`.

### Обновление

Для установки старше 0.13.0 обновитесь через уже используемый менеджер:

```bash
pipx upgrade deepseek-team
# либо: uv tool upgrade deepseek-team
# либо внутри активированного venv: python -m pip install --upgrade deepseek-team

deepseek-team hooks refresh --runtime auto --notify --json
```

Сохранённые настройки, учётные данные, подключённые проекты и интеграции
координаторов сохраняются; новая переменная для ключа необязательна и ничего не
меняет, пока не задана. Пользователям Codex и Claude Code достаточно обычного
refresh и новой сессии. Пользователи DSH, у которых уже есть принадлежащая пакету
строка bridge, могут выполнить `deepseek-team hooks refresh --runtime qwen` для
миграции прежней формы строки, затем перезагрузить профиль DSH (или перезапустить
DSH) и начать новую сессию. Начиная с 0.12.0 ту же работу выполняет
`deepseek-team update --runtime all`.

### Ограничения

- Bridge-плагин написан на JavaScript, и его собственный набор тестов запускается под
  Node; без Node (или `DEEPSEEK_TEAM_NODE`) этот тест пропускается, а протокол хуков
  на Python по-прежнему покрыт `tests/test_qwen_hooks.py`. Пакет не может ни
  проверить, ни подтвердить нативную загрузку профиля DSH: перезагрузите профиль
  или перезапустите DSH и начните новую сессию сами.
- Воркеры Qwen — такие же DeepSeek-воркеры: им нужен Linux с работающей
  песочницей Bubblewrap (и предварительные условия AppArmor там, где этого требует
  дистрибутив) до чтения любых учётных данных, и эту границу нельзя отключить. Сам
  DSH пакетом не изолируется, а покрытие хуков остаётся построчным и никогда не
  универсальным.
- Тесты без сети проверяют локальное поведение; реальное обращение к модели возможно
  только в отдельно разрешённой проверке с подключением к провайдеру. Нативные
  Windows и macOS по-прежнему не поддерживаются.
