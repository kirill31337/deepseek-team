# DeepSeek Team 0.8.9

**English** | [Русский](#русский)

This release stops host-only runtime and toolchain availability from being mistaken
for readiness inside the managed worker namespace, and makes failed checks
diagnosable and rerunnable without another model request. It changes no hook
definition, delegation/access setting, credential location or publication step.

- **Namespace-verified runtime selection.** A default runtime name is no longer
  trusted because it works on the host. Candidates are enumerated in `PATH` order,
  then `/usr/local/bin` and `/usr/bin`, and the first one that really runs in the
  prepared sparse namespace is selected. `auto` may try Codex and then Claude; an
  explicit `--codex`/`--claude` pin is probed alone and its failure is fatal, so it
  is never silently replaced by a PATH, system or cross-runtime fallback. `--version`
  and the required capability help are probed locally before the provider key is
  read, under a shared total job deadline; deadline expiry is a code-124 budget
  error that stops fallback. See [Hardening](https://github.com/kirill31337/deepseek-team/blob/main/docs/HARDENING.md).
- **Declarative workspace preparation.** `workspace prepare` gains repeatable
  `--tool NAME=HOST_DIR`, `--copy SOURCE=REL_DEST`, `--env NAME=VALUE`,
  `--probe COMMAND` and `--save-project`. `--tool` copies an explicitly selected
  software directory into the private `.deepseek-tools/NAME` area, bound read-only
  inside the namespace; explicit copies stay writable in the owned copy. The legacy
  `workspace prepare ID -- COMMAND ARG ...` form is unchanged and still runs on the
  coordinator host with prepared workspace variables and `PATH`. `--probe` commands
  run only inside the worker namespace before any model key. `--save-project` stores
  a private recipe that replays declarations into later copies; it never executes or
  replays host commands. See the [toolchain guide](https://github.com/kirill31337/deepseek-team/blob/main/docs/TOOLCHAINS.md).
- **Reusable redacted evidence.** Check output is retained per stream up to 65,536
  bytes, redacted for known sensitive values, and published owner-only in the private
  `diagnostics/` directory of the workspace. Larger output is drained and marked
  truncated, and a timed-out command's process group is cleaned up. Timeout and
  launch failures are environment evidence; ordinary project-check failures stay
  operational evidence.
- **Baseline-red bugfix work.** Declared checks are captured as a baseline before the
  model runs. A nonzero baseline is evidence, not a blanket rejection, so a bugfix
  assignment may proceed against an already-red suite. Automatic terminal feedback for
  a failed project check is now neutral `unknown`; only a reviewed explicit
  quality/disposition grades the worker. Causes distinguish `unknown`,
  `baseline_failure` and `regression_candidate`, and a matching exit code alone is not
  proof of a matching root cause.
- **Verification without another model call.** `workspace verify ID [--check COMMAND]
  [--timeout SECONDS] [--json]` rebuilds the prepared environment and sparse namespace,
  reruns the declared or supplied checks, and appends a unique verification run. It
  never loads the provider key, starts a relay or starts a model, and it preserves the
  original worker status, error, checks and quality. Private fingerprints of explicitly
  registered prepared inputs (for example an ignored `local.properties`) are recorded
  separately from the source patch and regular worker changes.
- **Offline full-access doctor.** In `--offline` mode `doctor` checks a managed
  full-access runtime by actually launching a candidate in a disposable empty sparse
  namespace with a per-candidate context; it allocates no model job and reads no key.
  The read-only native Codex / outer read-only Claude boundary is unchanged.

Upgrade from 0.8.7 or 0.8.8 as usual, then run `setup` once for each coordinator
runtime you installed and confirm readiness offline:

```bash
pipx upgrade deepseek-team
deepseek-team setup --runtime codex --no-key   # or claude / both
deepseek-team doctor --runtime codex --offline
```

`setup` refreshes the user-level hooks and both managed instruction files in the
repository you run it from when they are already attached. Every other attached
project refreshes its own blocks on its next session or prompt; run `init` only to
attach a project for the first time or to deliberately repair its managed blocks.
Linked human-maintained guides are never overwritten. Installing or upgrading with
pip, pipx or uv does not run setup automatically, and this release performs no
installation, configuration or credential change beyond the version bump.

Missing prerequisites can now be detected earlier — including a host-only launcher
whose sibling target is absent inside the namespace — but no release can eliminate
every external failure. Prepare real project dependencies instead of stubbing them;
the release ships 0.8.9 metadata and an installable artifact, and publication is a
separate action.

## Русский

Этот релиз не позволяет принимать доступность среды выполнения и инструментов на
хост-системе за готовность внутри управляемого пространства имён воркера, а также
делает неудачные проверки диагностируемыми и повторяемыми без нового запроса к модели.
Определения хуков, настройки делегирования и доступа, расположение учётных данных и
порядок публикации не меняются.

- **Выбор среды выполнения с проверкой в пространстве имён.** Имя среды по умолчанию
  больше не считается надёжным только потому, что оно работает на хост-системе.
  Кандидаты перебираются в порядке `PATH`, затем `/usr/local/bin` и `/usr/bin`, и
  выбирается первый, который действительно запускается в подготовленном разреженном
  пространстве имён. `auto` может сначала попробовать Codex, затем Claude; явное
  указание `--codex`/`--claude` проверяется отдельно, и его ошибка не приводит к
  подмене через `PATH`, системную или другую среду выполнения. `--version` и справка
  о требуемых возможностях проверяются локально до чтения ключа провайдера, в рамках
  общего предельного времени задания; истечение срока — это ошибка бюджета с кодом
  124, после которой резервный вариант не подбирается. См.
  [Изоляцию и безопасность](https://github.com/kirill31337/deepseek-team/blob/main/docs/HARDENING.ru.md).
- **Декларативная подготовка рабочей копии.** У `workspace prepare` появились
  повторяемые параметры `--tool NAME=HOST_DIR`, `--copy SOURCE=REL_DEST`,
  `--env NAME=VALUE`, `--probe COMMAND` и `--save-project`. `--tool` копирует явно
  выбранный каталог программного обеспечения в приватную область
  `.deepseek-tools/NAME`, доступную внутри пространства имён только для чтения;
  явно скопированные данные остаются доступными для записи в рабочей копии.
  Прежняя форма `workspace prepare ID -- COMMAND ARG ...` сохранена и по-прежнему
  выполняется на хост-системе координатора с подготовленными переменными и `PATH`.
  Команды `--probe` запускаются только внутри пространства имён воркера до
  обращения к ключу модели. `--save-project` сохраняет приватный рецепт, который
  воспроизводит объявления в последующих копиях; он никогда не выполняет и не
  воспроизводит команды хост-системы. См. [гид по инструментам](https://github.com/kirill31337/deepseek-team/blob/main/docs/TOOLCHAINS.ru.md).
- **Повторно используемые отредактированные свидетельства.** Вывод проверок хранится
  отдельно по потокам объёмом до 65 536 байт, из него удаляются известные
  чувствительные значения, а публикуется он только для владельца в приватном
  каталоге `diagnostics/` рабочей копии. Больший вывод продолжает считываться и
  помечается как усечённый, а группа процессов команды с истёкшим временем
  очищается. Таймаут и ошибка запуска — это свидетельства среды; обычные ошибки
  проверок проекта остаются эксплуатационными свидетельствами.
- **Исправление ошибок при изначально красных проверках.** Объявленные проверки
  снимаются как базовая линия до запуска модели. Ненулевой результат — это
  свидетельство, а не автоматический отказ, поэтому задание на исправление может
  выполняться при уже красном наборе проверок. Автоматический итоговый отзыв о
  неудачной проверке проекта теперь нейтральный `unknown`; качество воркера
  оценивает только явная проверка и решение координатора. Причины различают
  `unknown`, `baseline_failure` и `regression_candidate`; совпадение кода выхода
  само по себе не доказывает совпадение первопричины.
- **Проверка без нового запроса к модели.** `workspace verify ID [--check COMMAND]
  [--timeout SECONDS] [--json]` заново собирает подготовленную среду и разреженное
  пространство имён, повторяет объявленные или заданные проверки и добавляет
  уникальный запуск проверки. Команда никогда не читает ключ провайдера, не
  запускает релей и модель и сохраняет исходный статус, ошибку, проверки и качество
  воркера. Приватные отпечатки явно зарегистрированных подготовленных входных файлов
  (например, игнорируемого `local.properties`) записываются отдельно от патча
  исходного кода и обычных изменений воркера.
- **Офлайн-диагностика полного доступа.** В режиме `--offline` команда `doctor`
  проверяет среду управляемого полного доступа, действительно запуская кандидата в
  одноразовом пустом разреженном пространстве имён с контекстом для каждого
  кандидата; задание модели не создаётся и ключ не читается. Граница нативного
  режима только для чтения для Codex и Claude без изменений.

Обновитесь с 0.8.7 или 0.8.8 как обычно, затем один раз выполните `setup` для каждого
установленного координатора и подтвердите готовность офлайн:

```bash
pipx upgrade deepseek-team
deepseek-team setup --runtime codex --no-key   # либо claude / both
deepseek-team doctor --runtime codex --offline
```

`setup` обновляет пользовательские хуки и оба управляемых файла инструкций в
репозитории, откуда он запущен, если они уже подключены. Остальные подключённые
проекты обновляют свои блоки при следующей сессии или запросе; запускайте `init`
только для первого подключения проекта или намеренного исправления его управляемых
блоков. Поддерживаемые вручную linked-гиды никогда не перезаписываются. Установка или
обновление через pip, pipx или uv не запускает setup автоматически, и этот релиз не
вносит изменений в установку, настройку или учётные данные сверх смены версии.

Отсутствующие предварительные требования теперь можно выявлять раньше — включая
случай, когда работающий на хосте лаунчер ссылается на отсутствующий в пространстве
имён соседний файл, — но ни один релиз не может устранить все внешние сбои.
Готовьте настоящие зависимости проекта, а не заглушки; релиз поставляет метаданные
0.8.9 и устанавливаемый артефакт, а публикация выполняется отдельно.
