# DeepSeek Team 0.10.4

## English

0.10.4 corrects routing diagnostics, storage readiness, shell classification,
Claude policy hooks and saved toolchain preparation.

- Unknown, high and protected risk have distinct diagnostics. New substantial
  Auto plans identify all missing semantic feature fields before routing; an
  explicit `unknown` remains valid. Kotlin is accepted by routing and lessons.
  `deepseek-team routing schema --json` exposes valid values and defaults, and
  invalid-value errors list the allowed choices.
- `deepseek-team doctor` now checks the shared private XDG/HOME-config storage
  pool used by workspace and runtime allocations on the target filesystem, in
  addition to the selected state root. Readiness failures include actionable
  remedies. Pool validation creates no reservation and does not chmod existing
  entries, follow unsafe links or relocate retained data.
- Literal shell redirections to standard sinks such as `/dev/null`,
  `/dev/stdout` and `/dev/stderr` are no longer reported as project writes.
  Real writes, dynamic destinations and uncertain working directories retain
  their scope checks, including when mixed with standard-sink redirections.
- A public CLI regression covers adding a new plan deliverable after an
  assignment failed: JSON output is returned, existing assignment IDs and
  failure history remain intact, identical replans are no-ops, and edits to
  started scope return a visible error.
- Claude hook installation now records the absolute `deepseek-team` launcher
  path, so a hook does not depend on the interactive `PATH`. The `PreToolUse`
  command hook uses `onFailure: "block"`; native failure blocking requires
  [Claude Code 2.1.295](https://github.com/anthropics/claude-code/releases/tag/v2.1.295)
  or later and is verified with 2.1.316. Internal admission
  failures and malformed hook input use explicit blocking responses.
- Real-permissions CI now pins the tested Claude Code 2.1.316, matching
  fail-closed native hook support.
- Newly saved toolchain recipes refer to immutable, content-addressed copies in
  the coordinator's private cache instead of a checkout or host path. Entries
  are validated under the shared cache lock, materialized independently into
  each workspace, and bounded by explicit finite byte and inode limits. Missing,
  stale or unsafe entries produce actionable re-preparation guidance. Legacy
  recipes with external copy sources require explicit re-saving and are
  preserved without silent migration. A complete offline JVM recipe, including the
  prepared JDK runtime configuration and truststore, can be replayed without a
  host toolchain fallback; declared probes still decide readiness.
- Linked corrections retain the reviewed execution identity after successful
  provider-free toolchain preparation. Preparation attempts remain separate;
  pending, failed, unknown or stale execution history still blocks safely.

Upgrade through the same package manager, then refresh setup and local checks:

```bash
pipx upgrade deepseek-team
deepseek-team setup --runtime codex --no-key   # or claude / both
deepseek-team doctor --runtime codex --offline
```

## Русский

0.10.4 исправляет диагностику роутинга, проверку хранилища, классификацию команд
оболочки, хуки Claude и сохранение подготовленного инструментария.

- Неизвестный, высокий и защищённый риск получают разные объяснения. Новый
  существенный Auto-план перечисляет недостающие смысловые признаки до роутинга;
  явное значение `unknown` остаётся допустимым. Kotlin поддерживается в роутинге
  и lessons. Команда `deepseek-team routing schema --json` показывает значения
  и умолчания; ошибки валидации перечисляют допустимые варианты.
- `deepseek-team doctor` теперь проверяет общий приватный пул хранилища в
  XDG/HOME-конфигурации, который используется для выделения ресурсов workspace и
  runtime на целевой файловой системе, в дополнение к выбранному корню
  состояния. При сбое готовности выводятся конкретные способы исправления, а
  проверка завершается отказом. Проверка пула не создаёт резервирование, не меняет
  права существующих записей, не следует по небезопасным ссылкам и не перемещает
  сохранённые данные.
- Литеральные перенаправления оболочки в стандартные приёмники, например
  `/dev/null`, `/dev/stdout` и `/dev/stderr`, больше не считаются записью в
  проект. Проверки реальных записей, динамических назначений и неопределённого
  рабочего каталога сохраняются и в смешанных командах.
- Публичная CLI-регрессия покрывает добавление нового пункта плана после сбоя
  задания: команда возвращает JSON, сохраняет прежние идентификаторы и историю,
  повтор того же плана ничего не меняет, а правка уже начатой области завершается
  явной ошибкой.
- Установщик хуков Claude теперь записывает абсолютный путь к
  `deepseek-team`, поэтому хук не зависит от интерактивного `PATH`. Командный
  хук `PreToolUse` использует `onFailure: "block"`; нативная блокировка требует
  [Claude Code 2.1.295](https://github.com/anthropics/claude-code/releases/tag/v2.1.295)
  или новее и проверена на 2.1.316. Внутренние ошибки подготовки
  координации и некорректный ввод хука получают явный блокирующий ответ.
- CI с реальными правами теперь закрепляет проверенную версию Claude Code
  2.1.316, соответствующую нативной блокировке при сбое хука.
- Новые сохранённые рецепты инструментов ссылаются на неизменяемые копии с
  адресацией по содержимому в приватном кэше координатора, а не на рабочую
  копию или путь хост-системы. Записи проверяются под общей блокировкой кэша,
  независимо материализуются в каждую рабочую копию и ограничены явными
  конечными лимитами байтов и inode. Отсутствующие, устаревшие или небезопасные
  записи сопровождаются подсказкой о повторной подготовке. Старые рецепты с
  внешними источниками копий требуют явного повторного сохранения; исходные
  записи сохраняются без молчаливой миграции. Полный офлайн-рецепт JVM, включая
  подготовленную конфигурацию среды выполнения JDK и хранилище доверенных
  сертификатов, воспроизводится без запасного варианта с инструментами
  хост-системы; готовность по-прежнему определяют объявленные проверки.
- Связанные исправления сохраняют идентичность проверенного выполнения после
  успешной подготовки инструментов без провайдера. Попытки подготовки остаются
  отдельными; незавершённая, неудачная, неизвестная или устаревшая история
  выполнения по-прежнему безопасно блокирует продолжение.

Обновление выполняется тем же менеджером пакетов, затем обновите setup и
локальные проверки (команды выше).
