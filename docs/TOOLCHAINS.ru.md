# Подготовка инструментов и повторная проверка

[English](https://github.com/kirill31337/deepseek-team/blob/main/docs/TOOLCHAINS.md) | **Русский**

Управляемый воркер работает в разреженном пространстве имён Bubblewrap: он видит
собственную копию проекта, нужные каталоги среды выполнения и временный домашний
каталог, но **не** видит корень хост-системы, ваш домашний каталог, `/etc`,
`/usr/lib` или установленные SDK. Поэтому лаунчер, работающий на хост-системе,
может не запуститься внутри пространства имён, если соседний файл или помощник не
был туда смонтирован. Подготовка копирует явно выбранный набор инструментов в
собственную копию проекта, чтобы он действительно был виден там, а объявленные
smoke-проверки определяют готовность до чтения ключа провайдера.

На этой странице описаны реализованные команды `workspace prepare` и
`workspace verify`. Формулировки отдельных параметров соответствуют реальному
интерфейсу командной строки; актуальную справку можно получить командами
`deepseek-team workspace prepare --help` и `deepseek-team workspace verify --help`.

## Декларативная подготовка

```text
deepseek-team workspace prepare ID [--tool NAME=HOST_DIR] [--copy SOURCE=REL_DEST]
  [--env NAME=VALUE] [--probe COMMAND] [--save-project]
  [--resume-after-failure] [-- COMMAND ARG ...]
```

Каждый параметр можно повторять, а чисто декларативная подготовка (без прежней
команды) допустима. Блокировка копии удерживается на всё время операции, а в
приватных метаданных рабочей копии сохраняется рецепт версии 1.

- **`--tool NAME=HOST_DIR`** копирует явно выбранный каталог программного
  обеспечения хост-системы в `.deepseek-tools/NAME`. Имя должно соответствовать
  `[A-Za-z][A-Za-z0-9_-]{0,63}`. Материализованное дерево монтируется внутри
  пространства имён **только для чтения**, поэтому воркер не может изменить
  скопированный SDK/JDK. Символические ссылки материализуются, только если они
  остаются внутри выбранного корня программного обеспечения; выход за его пределы
  и циклы отклоняются до публикации.
- **`--copy SOURCE=REL_DEST`** копирует один явный несекретный файл или каталог
  кэша сборки в относительный путь внутри рабочей копии. Скопированные кэши
  остаются **доступными для записи** в собственной копии. Назначение не может
  выйти за пределы копии, содержать `.`/`..`, NUL, CR или LF, затрагивать
  служебные данные Git, пересекаться с `.deepseek-tools/`, быть похожим на
  учётные данные или перезаписывать отслеживаемый исходный код. Записанные
  назначения копий сохраняются в приватном `prepared_paths`, поэтому последующее
  изменение игнорируемого входного файла, например `local.properties`,
  фиксируется как свидетельство, а не попадает в патч.
- **`--env NAME=VALUE`** объявляет одну подготовленную переменную. Принимаются
  только `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `GRADLE_USER_HOME`,
  `M2_HOME`, `KOTLIN_HOME` и `PATH`; каждое значение-путь должно использовать
  литерал `{workspace}`, разрешающийся внутри копии. Каждый элемент `PATH` должен
  быть таким каталогом рабочей копии; подготовленный `PATH` добавляется в начало
  очищенного `PATH` вызывающего. `HOME`, переменные провайдера, переопределения
  хуков и конфигурации, а также переменные внедрения загрузчика не принимаются
  никогда.
- **`--probe COMMAND`** объявляет явную smoke-команду. Проверки запускаются только
  внутри пространства имён воркера, до чтения ключа провайдера, максимум 64
  проверки. Неудачная проверка — это сбой подготовки (`environment` /
  `probe_failure`), который останавливает задание; успех при этом не заявляется
  молча.
- **`--save-project`** сохраняет приватный рецепт, привязанный к каноническому пути
  исходного проекта в приватном корне состояния, который воспроизводит эти
  объявления в последующей копии того же проекта. Рецепт содержит только
  объявления и **никогда не выполняет и не воспроизводит автоматически команды
  хост-системы**. Некорректный, небезопасный, несовместимый или неудачный рецепт
  отклоняется безопасно; отсутствие рецепта сохраняет прежнее поведение. Рецепты,
  диагностика и хеши остаются в приватном состоянии вне патча исходного кода.
- **Прежняя форма `-- COMMAND ARG ...`** не меняется: она по-прежнему выполняется
  на хост-системе координатора в существующем безопасном окружении, а
  подготовленные переменные и `PATH` передаются ей. Держите артефакты и кэши
  внутри рабочей копии, а не в отдельном домашнем каталоге подготовки.

Повторная подготовка полностью заменяет набор объявлений: артефакты, которые
больше не объявлены, удаляются, а отслеживаемый исходный код ниже назначения
сохраняется, и его замена отклоняется. Артефакты подготовки добавляются в приватные
исключения Git рабочей копии (`.git/info/exclude`), а не в отслеживаемый файл
исключений продукта, поэтому они не появляются в diff воркера.

## Материализация Debian/OpenJDK

Для явно выбранной среды Java подготовка также материализует конфигурацию
времени выполнения, лежащую вне корня программного обеспечения: файлы ниже
`/etc/java-[0-9]+-openjdk/` и точное публичное хранилище доверенных сертификатов
`/etc/ssl/certs/java/cacerts`. Всё дерево `/etc` при этом не монтируется.

Пропускаются только две не относящиеся к среде выполнения публичные ссылки, без
чтения, перехода и монтирования их целей: `docs` на `/usr/share/doc/openjdk-N-*` и
`src.zip` / `lib/src.zip` на `/usr/lib/jvm/openjdk-N/src.zip`. Они учитываются как
пропущенные. Любая другая ссылка за пределы корня по-прежнему ведёт к отказу
подготовки. Это делает возможным запуск Debian Java и доступ к хранилищу
сертификатов, но не делает отсутствующую конфигурацию приемлемой — готовность
по-прежнему определяют объявленные реальные проверки Java и безопасности.

## Реалистичные рецепты

Каждая декларативная подготовка заменяет предыдущий набор объявлений. Укажите
все нужные проекту инструменты, копии, переменные и проверки в одной команде;
примеры ниже служат отдельными отправными точками, а не последовательными шагами.

Эти примеры делают инструменты видимыми и объявляют способ их проверки. Они не
обещают, что неподготовленный SDK или сборка завершатся успешно: готовность
по-прежнему определяет объявленная проверка или сборка проекта, а отсутствующий
компонент выявляется рано, а не выдаётся за реальную сборку.

**OpenJDK (структура пакета Debian/Ubuntu):**

```bash
deepseek-team workspace prepare WORKSPACE_ID \
  --tool JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 \
  --env 'JAVA_HOME={workspace}/.deepseek-tools/JAVA_HOME' \
  --env 'PATH={workspace}/.deepseek-tools/JAVA_HOME/bin' \
  --probe 'java -version' \
  --probe 'javac -version' \
  --save-project
```

**Android SDK и игнорируемый `local.properties`:**

```bash
deepseek-team workspace prepare WORKSPACE_ID \
  --tool JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 \
  --tool ANDROID_HOME=/opt/android-sdk \
  --copy /path/to/local.properties=local.properties \
  --env 'JAVA_HOME={workspace}/.deepseek-tools/JAVA_HOME' \
  --env 'ANDROID_HOME={workspace}/.deepseek-tools/ANDROID_HOME' \
  --env 'ANDROID_SDK_ROOT={workspace}/.deepseek-tools/ANDROID_HOME' \
  --env 'PATH={workspace}/.deepseek-tools/JAVA_HOME/bin:{workspace}/.deepseek-tools/ANDROID_HOME/cmdline-tools/latest/bin:{workspace}/.deepseek-tools/ANDROID_HOME/platform-tools' \
  --probe 'sdkmanager --version' \
  --probe 'adb version' \
  --save-project
```

`local.properties` обычно игнорируется и часто содержит только путь `sdk.dir`;
при регистрации через `--copy` он приватно отпечатывается. Копируйте его, только
если его `sdk.dir` указывает на подготовленное расположение — иначе SDK определяют
переменные `ANDROID_HOME` и `ANDROID_SDK_ROOT` выше. Абсолютный `sdk.dir` не
переписывается при создании другой копии по сохранённому рецепту: исключите
`--copy` из повторно используемого рецепта Android, если файл не остаётся
корректным в каждой копии, и явно подготовьте нужную локальную конфигурацию.
Ключ подписи (`.jks`,
`.keystore`) похож на учётные данные и намеренно отклоняется — никогда не
подготавливайте материал подписи.

**Кэш сборки Gradle (`GRADLE_USER_HOME` остаётся доступным для записи в копии):**

```bash
deepseek-team workspace prepare WORKSPACE_ID \
  --tool JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 \
  --tool GRADLE=/opt/gradle \
  --copy /path/to/.gradle/caches=gradle-home/caches \
  --env 'JAVA_HOME={workspace}/.deepseek-tools/JAVA_HOME' \
  --env 'PATH={workspace}/.deepseek-tools/JAVA_HOME/bin:{workspace}/.deepseek-tools/GRADLE/bin' \
  --env 'GRADLE_USER_HOME={workspace}/gradle-home' \
  --probe 'gradle --version' \
  --save-project
```

Затем проверьте внутри пространства имён воркера, не тратя запрос к модели.
Офлайн-диагностика по-прежнему проверяет только локальную готовность и
пространство имён; smoke-проверки и `workspace verify` запускают реальные команды:

```bash
deepseek-team workspace verify WORKSPACE_ID --check './gradlew --offline :app:assembleDebug'
```

Для офлайн-сборки нужен явный `--copy` скачанных обёрткой Gradle дистрибутивов или
настоящий бинарник `gradle` в подготовленном `PATH`; один только кэш не
гарантирует наличие Gradle.

## Повторная проверка без нового запроса к модели

```text
deepseek-team workspace verify ID [--check COMMAND] [--timeout SECONDS] [--json]
```

`workspace verify` заново собирает подготовленную среду и разреженное пространство
имён, воспроизводит сохранённый рецепт и повторяет объявленные или заданные
проверки. Если `--check` не указан, используются приватно записанные объявленные
проверки; пустой набор отклоняется. Команда **никогда не читает ключ провайдера,
не запускает релей и модель**.

- Код выхода `0` при успехе проверок, `65` при неудаче проверки и `124` при
  таймауте проверки.
- Уникальный запуск проверки добавляется в приватный `verification_runs` и
  связывается с исходным заданием/поручением, если оно было записано; исходный
  статус, ошибка, проверки и качество воркера сохраняются. Повторная проверка
  никогда не переписывает неудачную попытку или её оценку и не создаёт нового
  случая качества.
  Если публикация в журнал прервалась после сохранения записи копии, следующий
  запуск сначала опубликует её однократно в исходную попытку. Для runtime по
  умолчанию кандидаты ищутся заново; явно заданный путь остаётся закреплённым.
- Вывод каждого потока хранится объёмом до 65 536 байт, из него удаляются известные
  чувствительные значения, и он публикуется только для владельца в приватном
  каталоге `diagnostics/` рабочей копии; больший вывод продолжает считываться и
  помечается как усечённый. Для машиночитаемого результата используйте `--json`.
- Команда может проверить изначально неудачную копию, не возобновляя реализацию
  автоматически. Продолжение по-прежнему требует явного решения.

## Базовая линия и причины свидетельств

До запуска модели объявленные проверки снимаются как **базовая линия**. Ненулевой
результат — это свидетельство, а не автоматический отказ, поэтому задание на
исправление может выполняться при уже красном наборе проверок. После воркера сбои
остаются эксплуатационными: `kind` равен `environment` для свидетельств
таймаута/запуска/проверки и `verification` для обычных ошибок проверок проекта, а
совпадение кода выхода само по себе не доказывает совпадение первопричины.

| Причина | Значение |
| --- | --- |
| `baseline_failure` | Та же команда уже падала в базовой линии с идентичной неусечённой сигнатурой сбоя. |
| `regression_candidate` | Та же команда проходила в базовой линии и упала после воркера. |
| `unknown` | Ошибка проверки проекта без совпадающей сигнатуры базовой линии. |
| `timeout` / `launch_failure` / `probe_failure` | Причины среды; воркер не обвиняется. |

Автоматический итоговый отзыв о неудачной проверке проекта остаётся нейтральным
`unknown`, пока координатор не изучит фактический diff и свидетельства. Качество
воркера оценивает только явная проверка и решение координатора, а прежний явный
сбой воркера сохраняется, даже если последующая повторная проверка проходит.
