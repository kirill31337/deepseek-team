# Журнал доработок и правила делегирования

[English](https://github.com/kirill31337/deepseek-team/blob/main/docs/DELEGATION_LESSONS.md) | **Русский**

DeepSeek Team ведёт закрытый журнал по каждому проекту: что произошло с каждым переданным заданием, включая задания, которые не потребовали ни одной правки. На границе завершённой задачи координатор просматривает этот журнал и может обновить ограниченный набор правил планирования задач на основе записанных данных. Здесь описаны журнал, структурированная причина доработки, периодичность ревью и точный JSON, который подаёт координатор. Журнал хранит историю качества координации; правила — это совещательная подсказка для планирования, а не автоматический механизм управления.

## Чего здесь нет

- Фонового вызова модели нет. Приложение никогда не вызывает модель и не исполняет правило само.
- Оно не переписывает проектный `AGENTS.md` и исходники по выводу модели. Правила меняет только координатор и только явной подачей ревью.
- В этой функции веса маршрутизации не меняются. Журнал и его правила отделены от оценки и маршрутизатора; функция не читает и не пишет оценки маршрутизации, права доступа, принудительный `effort`, активацию или политику песочницы.
- Операционная система не умеет сама определять смысловую доработку. Решение принимает координатор после просмотра реального diff и заявленных проверок; инструмент лишь сохраняет это решение, а не выводит его.
- Сравнение «до/после» по количествам не доказывает, что улучшение вызвано правилом. Ревьюер сопоставляет повторяемость и сравнимые группы по `kind`/`effort`, включая чистые успехи, но журнал — описательное свидетельство, а не контролируемый эксперимент.

## Закрытое локальное состояние

Состояние привязано к одному разрешённому пути проекта и остаётся на локальной машине:

```text
~/.local/state/codex-deepseek/lessons/<sha256(разрешённый путь проекта)[:24]>/
```

- Исходы и ревью хранятся в SQLite-истории, доступной только на добавление. Повторная запись того же события с тем же содержимым идемпотентна и не дублируется.
- Markdown-файл правил генерируется из канонического версионированного набора правил, поэтому сгенерированный Markdown всегда можно восстановить из канонических правил.
- Запрос только на чтение при пустом состоянии не создаёт файлов. Параллельные события сохраняются за счёт блокировок и атомарной записи; файлы-симлинки отклоняются.
- Переиспользуйте существующие закрытые ссылки на свидетельства. Никогда не копируйте учётные данные и сырые логи модели в журнал, в файлы проекта или в Git.

Указывайте `--path PROJECT` в каждой команде `lessons`, чтобы журнал относился к нужному проекту.

## Запись исхода

Записывайте каждый проверенный результат через жизненный цикл координации — так же, как отзыв для маршрутизации:

```bash
deepseek-team coordination use --path "$PROJECT" \
  --task TASK_ID --assignment ASSIGNMENT_ID \
  --disposition incorporated --evidence "Заявленные проверки и ревью пройдены"
```

Если проверенный результат потребовал правки, добавьте структурированную причину через `--rework-json`. Флаг дополняет существующие `--disposition` и `--evidence`, а не заменяет их; внешнее `--evidence` остаётся проверяемым доказательством для решения.

```bash
deepseek-team coordination use --path "$PROJECT" \
  --task TASK_ID --assignment ASSIGNMENT_ID \
  --disposition needs-rework --evidence "В diff не обработан второй случай; тесты при этом проходят" \
  --rework-json /tmp/rework.json
```

В `/tmp/rework.json` должен быть объект JSON ровно с четырьмя ограниченными непустыми строковыми полями:

```json
{
  "cause": "brief_gap",
  "severity": "minor",
  "summary": "Воркер обработал первую форму входных данных, но оставил без обработки вторую.",
  "prevention": "Указывать в брифе обе допустимые формы входных данных и ожидаемый результат для каждой."
}
```

`cause` принимает одно из значений:

| Причина | Смысл |
| --- | --- |
| `worker_error` | Воркер ошибся там, где бриф этого не предполагал |
| `brief_gap` | Бриф задания был неполным или неоднозначным |
| `context_gap` | Нужный контекст был недоступен воркеру |
| `requirements_changed` | Требование изменилось после начала задания |
| `integration` | Дефект проявился при объединении принятой работы |
| `environment` | Причина в инструментах, песочнице или среде исполнения |
| `mixed` | Одновременно применимы несколько причин |
| `unknown` | Причина ещё не определена — явный и допустимый вывод |

`severity` принимает `minor`, `major`, `redo` или `unknown`. `unknown` — полноценное значение для обоих полей: лучше указать его, чем угадывать. Неизвестная причина никогда не учитывается в пороге ревью по одинаковой причине, а неизвестная серьёзность сама по себе не становится меткой качества.

Решения остаются прежними: `incorporated`, `reproduced`, `needs-rework` и `rejected`. Несколько решений и повторные попытки по одному заданию — это один случай: позднее чистое включение не стирает ранний `needs-rework`, а отказ остаётся видимым отдельно. Если инструмент передаёт `--disposition needs-rework` или `--disposition rejected` без совместимой структурированной причины, записанные причина и серьёзность становятся `unknown`. Старые исходы без структурированной атрибуции остаются `unknown` и не дозаполняются задним числом. Чистому успеху `--rework-json` вообще не нужен, и именно чистые случаи образуют знаменатель, который делает ревью честным.

`--rework-json -` или `--quality-json -` читает соответствующий объект из стандартного ввода; если
используются оба флага, из стандартного ввода может читаться только один из них.

### Оценка качества

Новые самостоятельные успешные задания добавляют положительные наблюдения и повышают оценку сопоставимого класса. Серия успехов может снять ограничение по накопленному качеству; вес старых успехов и ошибок со временем уменьшается. Повторная запись одного задания не создаёт новых успехов. Отдельно порученный вызов на исправление получает собственную оценку, сохраняя историю исходного вызова.

Операциональная доработка и качество работы воркера — разные суждения. `--rework-json` объясняет, что
и почему потребовало правки; `--quality-json` фиксирует, насколько хорошо воркер выполнил выданные
ему требования. Если применимо и то и другое, передайте оба флага в одном вызове `coordination use`:

```bash
deepseek-team coordination use --path "$PROJECT" \
  --task TASK_ID --assignment ASSIGNMENT_ID \
  --disposition needs-rework --evidence "Принятая форма входных данных всё ещё не обработана" \
  --rework-json /tmp/rework.json --quality-json /tmp/quality.json
```

В `/tmp/quality.json` должен быть объект ровно вида `{grade, attribution, evidence}` с ограниченным
непустым доказательством не длиннее 4000 символов:

| Оценка | Вес | Смысл |
| --- | --- | --- |
| `met` | 1.0 | все выданные требования выполнены; косметические правки и правки по вкусу сохраняют полный кредит |
| `minor_gaps` | 0.8 | пропущено одно ограниченное выданное требование, основной результат пригоден |
| `major_gaps` | 0.3 | существенное выданное требование не выполнено |
| `unusable` | 0.0 | основной запрошенный результат не получен |
| `unassessable` | нейтрально | обоснованной оценки качества нет |

Атрибуция — `worker`, `shared`, `coordinator`, `environment` или `unknown`. Оценку качества даёт
только атрибуция `worker` или `shared` с оцениваемой категорией; доказательство для `shared` должно
назвать относимый к воркеру пробел относительно выданных требований и не должно угадывать числовую
долю ответственности. Результаты `infrastructure`, `cancelled` и `unknown` остаются нейтральными
независимо от оценки. Оценку и её доказательство даёт координатор; воркеры не оценивают себя сами.

Эти веса — объявленные значения рубрики, а не измеренные вероятности или доли вклада. Отсутствующий
бриф или недоступный контекст, а также требования, изменившиеся во время задания, сами по себе
нейтральны для качества работы воркера. Низкая стоимость правки не даёт права на `met` при серьёзном
дефекте: однострочная ошибка корректности или безопасности может оставаться серьёзной находкой, а
косметическая правка может сохранить полный кредит.

Если оценка не передана, сохраняется прежняя двоичная трактовка (`accepted` даёт 1, `rework` — 0,
`rejected` — 0) для совместимости, и в статистике она явно помечается как устаревшая. Старые двоичные
случаи можно переоценить, только добавив явную оценку, а не переписывая историю. Одно задание
остаётся одним случаем: если явных оценок несколько, сохраняется самая низкая оценка с атрибуцией
воркера (при равенстве — самая ранняя), поэтому позднее включение или нейтральная атрибуция не могут
«отмыть» известный дефект воркера; если явные оценки есть, но ни одна не оцениваема, случай
нейтрален; обычное включение без оценки качества никогда не стирает уже записанную оценку.

## Возврат доработки воркеру

Когда ревью показало, что результат требует правки, сначала запишите доказательство дефекта и исходное решение `needs-rework`. Небольшую тесно связанную правку координатор может внести сам, если запишет конкретную причину в `summary`/`prevention` доработки или во внешнее `--evidence`; существенные исправления обычно возвращаются в DeepSeek отдельным брифом на исправление. Такой бриф ссылается на исходное задание, называет конкретный дефект и его доказательство, даёт контекст, которого не хватало первой попытке, и содержит воспроизведение или исполняемые критерии приёмки. Передайте его отдельным заданием и только потом проверьте фактическую дельту и интегрируйте её. Размер правки и качество работы воркера — разные суждения: первая неудачная попытка сама по себе никогда не требует брать работу на себя, а однострочная правка может устранять серьёзный дефект. Архитектура, безопасность, интеграция и финальная верификация остаются за координатором.

Раннер запрещает слепые автоматические повторы, а успешно завершённое задание нельзя продолжить напрямую: для успешно завершённого задания нужна новая запланированная доработка со ссылкой на исходное. Упавшую и предварительно проверенную рабочую копию можно явно продолжить через `--resume-after-failure`. Ни один путь не может обойти `off`, пропустить песочницу воркера или автоматически расширить доступ.

Отдельно переданная доработка — это ещё один проверяемый вызов, а не второе решение по тому же заданию. Записывайте её своим `coordination use` и ссылайтесь на исходное задание в доказательствах; исходный `needs-rework` остаётся записанным и никогда не «отмывается» в чистую первую попытку. Ничто здесь не требует бесконечного цикла или искусственной фиксированной квоты попыток.

## Пакет для ревью

Команды чтения по умолчанию печатают понятный человеку текст, а с `--json` — структурированный JSON:

```bash
deepseek-team lessons status --path "$PROJECT" --json   # текущая версия, состояние ревью, счётчики, группы
deepseek-team lessons journal --path "$PROJECT" --json  # события в хронологическом порядке с устойчивым seq
deepseek-team lessons review --path "$PROJECT" --json   # пакет ревью, готовый к работе
deepseek-team lessons rules --path "$PROJECT" --json    # текущие правила и сгенерированный Markdown
```

Пакет `lessons review --json` содержит поля состояния (включая `version`, `through_event`, `review_due`, `due_reasons`, `cases_since_review`, `counts`, `cohorts`, `causes` и `severities`), а также:

- `expected_version` — версия, которую должен назвать подаваемый документ, чтобы быть принятым;
- `through_event` — последняя записанная последовательность; ревью подтверждает события до этой отметки;
- `reviewed_through` — последовательность, уже подтверждённая прошлым ревью;
- `cases` — события, сгруппированные по случаям, включая исходный контекст, доказательства и структурированную причину, если она есть;
- `rules` — действующие правила с идентификаторами подтверждающих случаев.

Берите `expected_version` и отметку из этого пакета, а не придумывайте их. `through_event`, не являющийся допустимой текущей последовательностью, или идентификатор случая, которого нет на момент отметки или раньше, делают подачу недействительной.

Пакет содержит достаточно прошлых свидетельств для обоснования каждого действующего правила, а в первом выпуске — все записанные случаи.

Контекст случая содержит исходное задание, его карту `features`, критерии приёмки и заявленные проверки, фактический runtime и `effort`, ссылки на рабочую копию/источник и на подготовленные и воркерские изменения, результаты заявленных проверок, явную оценку качества, если она передана, а также версию/идентификаторы/содержимое применимых правил, зафиксированные **до** исполнения. Снимок ссылается на `HEAD` источника, подготовленные изменения, проверки и, если доступно, дайджест или ссылку на промпт. Если в старом случае поле не было зафиксировано, оно остаётся явным `unknown`, а не выдумывается.

## Когда ревью пора проводить

Ревью становится нужным при выполнении любого из порогов с момента прошлого ревью:

- **10 различных новых или обновлённых случаев** — считаются именно случаи, всегда включая чистые успехи, а не сырые события; или
- **3 различных случая доработки с одинаковым `kind` задачи и одинаковой причиной, отличной от `unknown`.**

Повторные события по одному заданию не могут выполнить ни один порог: случай должен быть различным, а доработки с одинаковым видом и причиной — разными случаями. Координатор получает напоминание о ревью на границе завершённой задачи и затем при последующем разрешении сессии, промпта или политики. Это напоминание никогда не блокирует остановку пользователя, `off` или режим планирования и не создаёт повторного запрета Stop. В простое ничего не запускается: нет фонового вызова модели, автоматического переписывания и автоматического повтора.

## Подача ревью

Подайте документ ревью через `lessons review --apply`:

```bash
deepseek-team lessons review --path "$PROJECT" --apply /tmp/lessons-review.json
```

Документ должен быть ровно таким:

```json
{
  "expected_version": 3,
  "through_event": 17,
  "summary": "Заменить правило r2 и сохранить r1; brief_gap повторяется только в документирующих задачах с высоким effort.",
  "rules": [
    {
      "id": "r1",
      "when": { "kind": "documentation" },
      "condition": "У документирующей задачи больше одного целевого файла.",
      "action": "Перечислять в брифе все целевые файлы и ожидаемый заголовок для каждого.",
      "evidence": ["TASK-12/impl"]
    }
  ]
}
```

- `expected_version` должен совпадать с `expected_version` из пакета. Это оптимистическая проверка версии: если уже принято другое ревью, документ отклоняется. Новые исходы после указанной отметки остаются для следующего разбора.
- `through_event` должен быть допустимой последовательностью из пакета. Он не может идти назад и не может подтверждать параллельные более новые события; ревью подтверждает события только до этой отметки.
- `summary` — ограниченное непустое объяснение того, что изменилось и почему, в том числе для ревью без изменений.
- `rules` — полный набор правил на замену. У каждого правила ровно поля `id`, `when`, `condition`, `action` и `evidence`. Правило, отсутствующее в документе, удаляется.

Каждый `when` — объект сопоставления максимум со скалярными ключами `kind`, `domain`, `operation`, `runtime` и `effort`; лишние ключи не допускаются. Значение `effort` нормализует устаревшее `medium` в `high`. Правила сопоставляются с картой `features` планируемой задачи, поэтому подставленная карта, в которой нет ограничиваемого поля, не может совпасть с этим правилом. `evidence` — непустой список известных идентификаторов случаев, существующих на момент `through_event` или раньше.

Правила ограничены: не более **20 активных правил**, текст в каждом поле ограничен. Всё проверяется до любой записи. Каждое принятое ревью создаёт новый неизменяемый снимок версии; старые версии и их ревью остаются в истории, поэтому контекст, в котором работало прошлое задание, сохраняется. Версия растёт даже при явном ревью без изменений: чтобы обосновать отсутствие правок, подайте текущий набор правил без изменений (или пустой список `rules`, чтобы удалить все правила) с `summary`, объясняющим, почему данные не требуют изменений.

После ревью сгенерированный Markdown-файл правил перезаписывается из канонического набора правил со ссылками на доказательства.

## Правила совещательны и подчинены

Совпавшие правила применяются как подсказка при планировании до последующего делегирования и сохраняются на задании вместе с их точной версией. Они подчинены инструкциям пользователя, настройкам доступа, принудительному `effort` и требованиям песочницы: правило не может расширить доступ, изменить сохранённый профиль, отменить принудительный уровень effort или ослабить изоляцию. Эта функция не передаёт результаты применения правил в веса маршрутизации.

## Пример

После изучения конкретных случаев, если оснований менять правила нет, отправьте ревью без изменений из изученного пакета. Новые правила должны ссылаться на случаи, подтверждающие условие и действие; одного существования идентификатора в журнале недостаточно.

```bash
PROJECT=/path/to/repository
deepseek-team lessons review --path "$PROJECT" --json > /tmp/lessons-bundle.json

python3 - <<'PYTHON'
import json

bundle = json.load(open("/tmp/lessons-bundle.json"))
payload = {
    "expected_version": bundle["expected_version"],
    "through_event": bundle["through_event"],
    "summary": 'Случаи изучены; данных недостаточно для изменения текущих правил.',
    "rules": bundle["rules"],
}
json.dump(payload, open("/tmp/lessons-review.json", "w"), indent=2)
PYTHON

deepseek-team lessons review --path "$PROJECT" --apply /tmp/lessons-review.json
```

## Границы

- Правила — это подсказка для планирования, а не принуждение; реальными ограничителями остаются хуки и песочница воркера.
- Счётчики и таблицы групп описательны. Чистая группа после изменения правила не доказывает причинность, и никакой процент улучшения не заявляется.
- Журнал привязан к проекту и локален; он не публикуется и не используется для дообучения модели.
- `unknown` для атрибуции ожидаем для старых или действительно неоднозначных случаев и сам по себе не является ошибкой.
