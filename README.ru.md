# DeepSeek Team

[English](README.md) | **Русский**

DeepSeek Team — пакет для Linux, с которым **Codex и Claude Code могут поручать отдельные задачи воркерам DeepSeek**. Codex или Claude Code выступает координатором: распределяет работу и проверяет результат. Пакет поддерживает **профили делегирования 25/50/75%**, отдельную настройку доступа (`read-only` или `full-access`) и изолированные рабочие копии, которые можно использовать повторно.

**Координатор** определяет объём задачи, отвечает за архитектуру и безопасность, проверяет итоговые изменения, переносит их в основной проект, делает коммиты и выполняет действия в рабочей среде. **Воркеры DeepSeek** исследуют конкретные вопросы и проверяют код. В режиме `full-access` они также пишут код и документацию, запускают локальные тесты и сборки в отдельной рабочей копии.

Все воркеры DeepSeek используют `deepseek-flash`. Параметр `effort` задаёт глубину рассуждений модели. По умолчанию он равен `auto`: координатор выбирает `low`, `medium` или `high` для каждого задания. При необходимости можно сохранить фиксированное значение в настройках.

Codex и Claude Code могут подключать и собственных субагентов, если для этого есть конкретная причина. Такие субагенты дополняют воркеров DeepSeek, но не заменяют обязательные задания для них. Координатор проверяет полученный результат; заново проводить всё исследование или переписывать уже корректный код не нужно.

Проценты задают **ориентир для распределения работы**. Это не квоты на токены, время или строки кода и не гарантия точной доли вклада. В небольших задачах или задачах, которые трудно разделить, доля делегирования может быть ниже. По умолчанию действует прежний режим: **25% + access=auto → read-only**.

В версии **0.6.0** координатор может выбирать `effort` для каждого задания DeepSeek. Настройка `auto|low|medium|high` сохраняется между запусками. При обоснованной необходимости по-прежнему можно использовать собственных субагентов Codex и Claude Code. Воркеры DeepSeek работают изолированно на `deepseek-flash` и не могут делегировать задачи другим агентам. В версии 0.5.0 появились журнал координации и обработчики событий Codex для контроля работы координатора.

В текущем коде поддерживаются и хуки Claude Code. Оба координатора используют журнал заданий и общий для проекта переключатель `on/off`, состояние которого сохраняется между сессиями.

Для работы нужны **Linux, Python 3.11+, Git, Bubblewrap и Codex CLI или Claude Code CLI**. Можно использовать оба CLI. Для Ubuntu предусмотрена настройка AppArmor, которая позволяет запускать изоляцию без отключения системных ограничений на пользовательские пространства имён. Для обращений к модели нужен API-ключ DeepSeek. Дополнительные Python-библиотеки не требуются; Bubblewrap и AppArmor устанавливаются как системные компоненты.

## Установка в Ubuntu — рекомендуемый вариант

Установите CLI нужного координатора — Codex, Claude Code или оба — и выполните:

~~~bash
git clone https://github.com/kirill31337/deepseek-team.git
cd deepseek-team
python3 install.py --with-sandbox
export PATH="$HOME/.local/bin:$PATH"
deepseek-team sandbox status
~~~

Параметр `--with-sandbox` **разрешает установщику настроить системную изоляцию с правами администратора**. В Ubuntu он устанавливает пакеты `bubblewrap` и `apparmor`, устанавливает или перезагружает профиль `deepseek-team-bwrap`, а затем проверяет работу изоляции. AppArmor остаётся включённым, значение `kernel.apparmor_restrict_unprivileged_userns` не меняется.

Далее настройте нужного координатора:

~~~bash
# Только Codex
deepseek-team setup --runtime codex
deepseek-team hooks status
deepseek-team doctor --runtime codex --offline
deepseek-team init --coordinator codex
# В Codex откройте /hooks, проверьте хук DeepSeek Team и подтвердите доверие к нему.

# Только Claude Code
deepseek-team setup --runtime claude
deepseek-team hooks status --runtime claude
deepseek-team doctor --runtime claude --offline
deepseek-team init --coordinator claude
# Откройте новую сессию Claude и проверьте хуки через /hooks.

# Оба координатора
deepseek-team setup --runtime both
deepseek-team doctor --runtime both --offline
deepseek-team init --coordinator both
~~~

Установщик создаёт виртуальное окружение Python в `~/.local/share/codex-deepseek-team/venv` и добавляет две команды с одинаковым действием:

~~~text
deepseek-team
codex-deepseek-team   # прежнее имя команды, сохранённое для совместимости
~~~

Прежние имена Python-пакета и пространства имён сохранены для совместимости с существующими установками и скриптами.

### Обработчики событий Codex (хуки)

Начиная с версии **0.5.0**, стандартный установщик ищет Codex в `PATH` и добавляет или обновляет обработчики событий DeepSeek Team в `$CODEX_HOME/hooks.json`. Команда `deepseek-team setup --runtime codex` настраивает те же обработчики. Основная модель Codex и данные входа в OpenAI сохраняются.

Полезные команды:

~~~bash
deepseek-team hooks install
deepseek-team hooks status
deepseek-team hooks remove
~~~

Хуки действуют только в подключённых проектах. Чтобы включить контроль работы координатора в репозитории, выполните:

~~~bash
deepseek-team init --coordinator codex /path/to/project
~~~

Разрешение на запуск хуков выдаётся в самом Codex. Откройте `/hooks`, проверьте хук DeepSeek Team и подтвердите, что доверяете ему. DeepSeek Team не обходит эту проверку и не считает разрешение выданным без подтверждения в Codex. При обычном обновлении команда запуска хука остаётся прежней, поэтому **повторно запускать `init` в уже подключённых проектах не нужно**.

`hooks remove` удаляет только обработчики DeepSeek Team. Остальные пользовательские хуки сохраняются.

### Обработчики событий Claude Code

Стандартный установщик также проверяет наличие Claude Code в `PATH` и добавляет хуки DeepSeek Team в `~/.claude/settings.json`. Если задана переменная `CLAUDE_CONFIG_DIR`, используется файл `settings.json` из этого каталога. Команда `setup --runtime claude` устанавливает те же хуки. Выбранная модель, разрешения, данные входа и чужие обработчики сохраняются. Хуки начинают действовать в проекте после `deepseek-team init --coordinator claude`.

~~~bash
deepseek-team hooks install --runtime claude
deepseek-team hooks status --runtime claude
deepseek-team hooks remove --runtime claude
~~~

Параметр `--runtime both` выбирает обоих координаторов, а `--runtime auto` выбирает те CLI, которые найдены в `PATH`. Без этого параметра команды `hooks` по-прежнему относятся к Codex.

После установки откройте новую сессию Claude и проверьте `/hooks`. Команда `hooks status` проверяет записи в пользовательских настройках, но не может подтвердить, что текущая сессия их загрузила. Параметр Claude `disableAllHooks`, настройки организации или запуск с `--bare` могут отключать хуки. Установщик сохраняет эти настройки. Подробности есть в [документации Claude](https://code.claude.com/docs/en/hooks).

Если проект был подключён раньше, команда `deepseek-team init --coordinator claude .` обновит старый текст, где делегирование описывалось как работа только по инструкциям. Для включения новых хуков достаточно уже существующего маркера подключения. При дальнейших обновлениях пакета и переключении `on/off` повторять `init` не нужно.

## Установка по инструкции для агента

Можно поручить установку или обновление DeepSeek Team самому Codex. Откройте в нём нужный проект и отправьте следующий текст:

> Инструкция оставлена на английском, чтобы в обеих версиях README агент получал одинаковое задание.

~~~text
Install or update DeepSeek Team in this Linux project from https://github.com/kirill31337/deepseek-team. Use the repository's standard install.py; on Ubuntu use --with-sandbox unless a working DeepSeek Team sandbox is already configured. Preserve my existing Codex model/auth, DeepSeek Team settings, and credential. Configure Codex support without asking me to paste secrets into this prompt; if no DeepSeek key exists, leave secret entry to "deepseek-team auth set". Ensure the stable Codex lifecycle hooks are installed and healthy with "deepseek-team hooks install" and "deepseek-team hooks status". If this repository does not already contain the DeepSeek Team managed block in AGENTS.md, attach it with "deepseek-team init --coordinator codex ."; if it is already attached, do not re-run init just because the package was updated. Verify "deepseek-team --version", "deepseek-team sandbox status", "deepseek-team hooks status", and "deepseek-team doctor --runtime codex --offline". Do not use --os-sandbox off and do not weaken AppArmor/Bubblewrap. If the hooks require native Codex trust/review, use the Codex "/hooks" interface and approve/trust the DeepSeek Team package-owned hooks yourself when the current Codex environment permits it. Do not bypass Codex hook trust or modify trust state outside the native Codex mechanism. Afterwards verify with "deepseek-team hooks status". Only ask me to approve the hooks manually if native approval cannot be completed from the current Codex session.
~~~

В инструкции **нет API-ключа**. Она также не меняет уровень делегирования, режим доступа и значение `effort`. Настройте ключ отдельно командой `deepseek-team auth set`. Если нужны другие настройки вместо текущих или стандартных, явно задайте `delegation_level`, `access` и `effort`.

### Установка без прав администратора и ручная настройка

Без параметра `--with-sandbox` установщик не вызывает `sudo`:

~~~bash
python3 install.py
export PATH="$HOME/.local/bin:$PATH"
deepseek-team sandbox status
~~~

Если проверка `sandbox status` проходит успешно, настраивать AppArmor не нужно. Если Ubuntu блокирует Bubblewrap при `kernel.apparmor_restrict_unprivileged_userns=1`, установите профиль DeepSeek Team:

~~~bash
deepseek-team sandbox install-apparmor
deepseek-team sandbox status
~~~

Другой вариант — повторно выполнить `python3 install.py --with-sandbox`.

В других дистрибутивах Linux установите Bubblewrap через системный менеджер пакетов и выполните `deepseek-team sandbox status`. Профиль AppArmor из комплекта рассчитан на ограничение пользовательских пространств имён, действующее в Ubuntu.

**Не обходите ограничение Ubuntu командой** `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`. DeepSeek Team сохраняет это ограничение и при необходимости разрешает создание пользовательских пространств имён через отдельный профиль AppArmor.

Также можно установить пакет через `pipx install .` или в виртуальное окружение Python. В любом случае перед запуском воркеров нужно установить Bubblewrap и проверить его работу.

## Зачем нужны AppArmor и Bubblewrap

Ubuntu может запрещать непривилегированным приложениям создавать пользовательские пространства имён без явного разрешения AppArmor. Для этого в DeepSeek Team есть **отдельный профиль, который применяется только при явном вызове**:

~~~text
profile deepseek-team-bwrap flags=(unconfined) {
  userns,
}
~~~

Профиль выбирается командой `aa-exec -p deepseek-team-bwrap -- ...`. Он не привязывается к `/usr/bin/bwrap` на уровне системы, поэтому не заменяет профили дистрибутива или администратора и не конфликтует с ними. Этот профиль лишь разрешает создать начальное пользовательское пространство имён. **За изоляцию файловой системы и процессов отвечает Bubblewrap**.

По умолчанию воркер запускается только после успешной проверки изоляции. Порядок проверки:

1. Найти `bwrap` и проверить наличие нужных параметров.
2. Попробовать создать пользовательское пространство имён напрямую.
3. Если этому мешает действующее ограничение AppArmor в Ubuntu, повторить попытку через `aa-exec -p deepseek-team-bwrap`.
4. Если оба способа не сработали, остановить запуск **до чтения API-ключа DeepSeek**.

Автоматически переходить к запуску без изоляции пакет не будет.

## Режимы изоляции

В режиме `read-only` способ изоляции зависит от CLI, через который работает воркер. В режиме `full-access` и Codex, и Claude Code запускаются во внешнем окружении Bubblewrap с более строгими ограничениями: в нём доступны только необходимые каталоги и файлы.

### Изоляция в режиме `read-only`

#### Воркер Codex

В Linux Codex уже использует собственную изоляцию на основе Bubblewrap. Если запустить его внутри ещё одного пространства имён Bubblewrap и запретить создание вложенных пользовательских пространств имён, встроенная изоляция Codex перестанет работать.

Поэтому DeepSeek Team:

- до чтения ключа воркера проверяет, можно ли запустить Bubblewrap напрямую или через профиль AppArmor;
- создаёт временную обёртку для `bwrap`, доступную только в сессии воркера;
- помещает каталог с обёрткой в начало `PATH` воркера;
- позволяет **самому Codex** настроить изоляцию Linux через проверенный способ запуска `bwrap`;
- применяет к заданию встроенный режим Codex `read-only`.

Данные входа, история, правила, плагины, приложения и память основной сессии Codex не копируются. Воркер получает временные `HOME` и `CODEX_HOME` и только те настройки, которые нужны для подключения к DeepSeek.

#### Воркер Claude Code

В Claude Code нет аналогичной встроенной изоляции через Bubblewrap для файловых инструментов. Поэтому DeepSeek Team запускает всю среду выполнения Claude **внутри отдельного окружения Bubblewrap**:

- корневая файловая система доступна только для чтения;
- для процессов, пользователей, IPC и UTS создаются отдельные пространства имён;
- дополнительные привилегии Linux (capabilities) сбрасываются;
- `/tmp` и `/var/tmp` изолированы от основной системы;
- настоящий домашний каталог пользователя скрыт; необходимые для запуска CLI каталоги подключаются отдельно, только для чтения;
- после подключения этих каталогов известные хранилища учётных данных снова скрываются;
- временный домашний каталог воркера доступен для записи;
- репозиторий или рабочее дерево Git доступно только для чтения;
- параметр `--disable-userns` запрещает процессам воркера создавать вложенные пользовательские пространства имён.

Claude запускается с `--bare`, без сохранения сессии. Из встроенных инструментов доступны только `Read,Glob,Grep`. Bash, веб-инструменты и запуск агентов недоступны; инструменты MCP также запрещены.

### Изоляция рабочих копий в режиме `full-access`

В режиме `full-access` DeepSeek Team запускает и Codex, и Claude в окружении Bubblewrap с минимальным набором доступных каталогов. В него входят рабочая копия, созданная пакетом, каталоги, необходимые для запуска CLI, временный домашний каталог и служебный каталог текущего запуска. Служебные файлы Git подключаются только для чтения. Параметр `--unshare-net` изолирует сеть: воркер не может обращаться к произвольным сервисам основной системы или внешней сети.

Запросы к API DeepSeek проходят только через специальный ретранслятор в основной системе. Он соединён с изолированным окружением через отдельный Unix-сокет для каждого запуска и локальный сетевой мост внутри этого окружения. Настоящий API-ключ остаётся у ретранслятора; воркер получает только служебный локальный ключ. Ретранслятор обращается к фиксированному адресату и обслуживает только запросы к API, необходимые для поддерживаемых протоколов Codex и Claude. Использовать его как универсальный прокси нельзя.

Таким образом, `full-access` даёт **полный доступ к выделенной рабочей копии**. Остальные репозитории пользователя, исходная копия с незакоммиченными изменениями, секреты, рабочие базы данных, системные сервисы и ключи для развёртывания остаются недоступны. Воркер также не может публиковать результаты, переносить изменения в основной репозиторий или делать коммиты.

### Доступ к сети в режиме `read-only`

Воркер Claude в режиме `read-only` обращается к DeepSeek напрямую, поэтому для него внешнее окружение Bubblewrap **не изолирует сеть**. При этом модели недоступны сетевые инструменты Claude. Codex использует собственные правила изоляции и доступа к сети.

## API-ключ DeepSeek

Codex и Claude Code используют один сохранённый API-ключ DeepSeek:

~~~bash
deepseek-team auth set       # скрытый ввод в терминале
deepseek-team auth status    # только наличие/отсутствие
~~~

Ключ хранится в `~/.config/codex-deepseek/api-key`. Права доступа: `700` для каталога и `600` для файла. Если задана переменная `DEEPSEEK_API_KEY`, используется её значение. В автоматизированных сценариях передавайте ключ из хранилища секретов в `deepseek-team auth set --stdin`. Не указывайте ключ в аргументах команд, файлах репозитория или заданиях для воркеров.

## Как включить или отключить DeepSeek Team

Выполните команду из каталога проекта или попросите Codex либо Claude Code сделать это:

~~~bash
deepseek-team off       # Отключить новые задания DeepSeek в этом проекте
deepseek-team on        # Включить обратно
deepseek-team status    # Показать действующее и сохранённое состояние
~~~

Например: «Выключи DeepSeek Team в этом проекте» или «Включи DeepSeek Team обратно». Это команды терминала, а не встроенные команды чата с `/`. Для обоих координаторов действует один переключатель.

Выбор сохраняется между сессиями и после обновления пакета. Состояние хранится локально для вашего пользователя, отдельно для каждой рабочей копии, в каталоге `${XDG_CONFIG_HOME:-~/.config}/deepseek-team/activation/`. В Git ничего не добавляется. Команды работают и из подпапок проекта. Можно явно указать путь: `deepseek-team off /path/to/project`. Команда `status --json` выводит действующее состояние, сохранённый выбор и источник настройки. Если вы находитесь вне репозитория Git, укажите путь к проекту.

По умолчанию делегирование включено. Команда `off` запрещает запуск новых воркеров, в том числе в ранее созданных рабочих копиях этого проекта. Со следующего события хуки Codex и Claude перестают требовать делегирование и блокировать работу координатора. Проверки с обращением к API также учитывают выключатель. Уже запущенные воркеры продолжают работу; их результаты и записи в журнале сохраняются. Команда `on` возвращает делегирование с прежними настройками доступа, процента и глубины рассуждений. Ключи и файлы инструкций проекта не меняются. Команда не устанавливает хуки и не подключает новый проект: для первоначальной настройки по-прежнему нужны `setup` и `init`.

Переменные `DEEPSEEK_TEAM_DISABLED=1` и `CODEX_DEEPSEEK_DISABLED=1` имеют приоритет над сохранённым выбором. Если одна из них задана, команда `on` сохранит включённое состояние, но сообщит, что делегирование останется отключённым до удаления переменной. Команда `config show --effective --instructions` тоже показывает состояние и при отключении предписывает координатору выполнять работу самостоятельно.

Оба координатора получают актуальное состояние через установленные и включённые хуки. Сама команда запуска воркера тоже проверяет выключатель, даже если в чате остались старые инструкции. В ранее подключённом проекте при желании можно один раз обновить блоки инструкций командой `deepseek-team init --coordinator both .`, чтобы добавить описание переключателя. Если используется только один координатор, укажите `codex` или `claude`. Для самих переключений повторный `init` не нужен.

## Профили делегирования и доступ

Для каждого параметра значение выбирается независимо. Приоритет настроек, от высшего к низшему:

**Аргументы командной строки → настройки проекта → глобальные настройки → значения по умолчанию.**

| Профиль | `access=auto` | Как распределяется работа |
| --- | --- | --- |
| **25%** | `read-only` | Воркеры исследуют отдельные вопросы, ищут причины ошибок и проверяют код. Основную реализацию выполняет координатор. |
| **50%** | `full-access` | Координатор сначала поручает воркерам независимые части реализации и тесты к ним. За собой оставляет архитектуру, интерфейсы и интеграцию. |
| **75%** | `full-access` | Воркерам поручают большую часть работы, которую можно отделить: код, тесты, документацию и независимую проверку. Одновременно можно задействовать до трёх воркеров, если их задания не зависят друг от друга. |

Режим доступа можно задать независимо от процента. Явно выбранный `read-only` действует и при 50/75%, а `full-access` можно включить даже при 25%. Изменение процента не сбрасывает заданный `access`. Чтобы снова выбирать доступ по профилю, верните `access` в `auto`.

### Модель DeepSeek, глубина рассуждений и субагенты координатора

Все воркеры DeepSeek Team используют **`deepseek-flash`**. Переключение между Flash и Pro не предусмотрено. По умолчанию параметр `effort` равен **`auto`**: координатор Codex или Claude выбирает `--effort low|medium|high` для каждого задания. Значение `low` подходит для простых, механических задач и обзорного поиска; `medium` — для обычной работы; `high` — для сложной отладки, анализа связей между файлами и тщательной независимой проверки. Если воркер запущен напрямую и координатор не выбрал глубину рассуждений, при запуске используется `medium`.

Координатор Codex или Claude может использовать собственных субагентов. В плане крупной задачи для такой работы указывают `"executor": "native-agent"` и конкретную причину в `"delegation_reason"`. Это полезно, если работу можно вести параллельно, ей нужен отдельный контекст или возможности среды самого координатора. Однако такие задания **не заменяют обязательное делегирование воркерам DeepSeek** при профилях 50/75. Решения, закреплённые за координатором, остаются его ответственностью. Воркеры DeepSeek не могут запускать других агентов или передавать им задачи.

Примеры:

~~~bash
# Настройки проекта
deepseek-team config set --project --delegation-level 50 --access auto

# Глобальные настройки пользователя
deepseek-team config set --global --delegation-level 25 --access read-only

# Действующие настройки и источник каждого значения
deepseek-team config show --effective
deepseek-team config show --effective --json

# Задать постоянный effort для проекта вместо выбора координатором
deepseek-team config set --project --effort high

# Или задать его глобально
deepseek-team config set --global --effort high

# Снова поручить выбор effort координатору
deepseek-team config set --project --effort auto

# Переопределить настройки для одного задания
deepseek-team worker --runtime codex --delegation-level 75 --access full-access --effort high
~~~

Настройки проекта хранятся в `.deepseek-team.toml`, глобальные настройки — в пользовательском каталоге конфигурации XDG. Для `effort` действует общий порядок приоритетов: аргумент командной строки для конкретного задания, настройки проекта, глобальные настройки, затем значение по умолчанию (`auto`). При запуске задания фиксируется текущий набор настроек. Последующие изменения не влияют на уже запущенный процесс.

`config show --effective --instructions --runtime codex|claude` выводит актуальные инструкции для координатора. Блоки, которые пакет добавляет в `AGENTS.md` и `CLAUDE.md`, требуют проверять действующие настройки перед каждым заданием. Так координатор не полагается на устаревший процент, записанный в файле.

`doctor` определяет и выводит те же действующие настройки. Если выбран `full-access`, команда проверяет доступные возможности среды выполнения. С параметром `--os-sandbox off` проверка режима `full-access` не допускается.

## Контроль работы координатора

Начиная с версии 0.5.0, DeepSeek Team ведёт журнал координации вне репозитория. В нём сохраняются идентификаторы сессий, задач и рабочих копий, ожидаемые результаты, задания воркеров, необходимые зависимости и проверки, изменения файлов, внесённые именно воркерами, полученные результаты и решения об их использовании, а также технические ограничения. Журнал предназначен для учёта работы; функций планировщика заданий или системы управления проектами в нём нет.

Стандартный установщик и команда `deepseek-team setup --runtime codex` добавляют хуки DeepSeek Team в пользовательский файл `$CODEX_HOME/hooks.json`. Они начинают действовать только после подключения репозитория командой `deepseek-team init --coordinator codex`. Для разрешения их запуска откройте `/hooks` в Codex, проверьте хук и подтвердите доверие к нему. DeepSeek Team не обходит эту проверку и не принимает решение за Codex.

Claude использует тот же журнал через свои пользовательские хуки. Для их работы проект должен быть подключён командой `init --coordinator claude`. В обоих случаях обрабатываются следующие события:

- `SessionStart` и `UserPromptSubmit` передают координатору текущее состояние работы и восстанавливают его после сжатия контекста.
- `PreToolUse` может заблокировать изменение исходников до выполнения команды, если план распределения работы отсутствует или нарушает правила, изменения выходят за рамки плана либо затрагивают файлы, над которыми ещё работает воркер.
- `Stop` просит продолжить работу, если остались незавершённые задания или результаты без решения координатора. В Claude при повторном вызове с `stop_hook_active=true` хук сообщает об оставшейся работе и сохраняет задачу незавершённой в журнале, но больше не блокирует остановку. Это защищает сессию от зацикливания.

В Claude проверка охватывает `Edit`, `Write`, `NotebookEdit` и распознаваемые команды `Bash`, которые изменяют файлы. Пути сопоставляются с планом проекта, в том числе когда Claude передаёт абсолютный путь. В режиме планирования Markdown-файлы из каталога планов Claude можно редактировать до регистрации распределения работы; событие `Stop` оставляет задачу открытой. Это исключение учитывает стандартный каталог и `plansDirectory` из пользовательских, проектных и локальных настроек.

Команды оболочки распознаются по известным шаблонам: хук не перехватывает все возможные способы записи через произвольные команды или внешние инструменты. События собственных субагентов Claude не создают и не завершают задачу координатора; его блокировки на них не распространяются. За изоляцию воркеров отдельно отвечает системная песочница.

При **75/full-access** воркерам по умолчанию можно поручать независимые части реализации, тесты, тестовые данные, документацию и метаданные без секретов. Запустить одного воркера для реализации или проверки недостаточно, если координатор без предусмотренного правилами основания оставляет себе всю остальную работу, пригодную для делегирования. При **50/full-access** одной проверки кода воркером также недостаточно, когда ему можно поручить часть реализации, тестов или документации. Режим доступа действует независимо: явно заданный `read-only` не разрешает запись при любом профиле.

Перед изменением исходников в крупной задаче координатор регистрирует план с конкретными ожидаемыми результатами:

~~~bash
deepseek-team coordination plan --task TASK_ID <<'JSON'
{
  "classification": "substantial",
  "deliverables": [
    {
      "id": "implementation",
      "kind": "implementation",
      "scope": ["src/example.py"],
      "executor": "worker",
      "acceptance": ["focused behavior implemented"],
      "dependencies": [{"kind": "command", "value": "python3"}],
      "checks": ["python3 -m unittest tests.test_example -q"]
    }
  ]
}
JSON
~~~

Идентификатор задания из плана указывается при запуске воркера:

~~~bash
deepseek-team worker --runtime codex --effort medium \
  --coord-task TASK_ID --coord-assignment ASSIGNMENT_ID <<'TASK'
Implement the assigned deliverable and satisfy its registered acceptance criteria.
TASK
~~~

Начало и завершение запуска, идентификатор рабочей копии, изменения воркера и заявленные проверки записываются автоматически. Проверив результат, координатор отмечает, как он его использовал:

~~~bash
deepseek-team coordination use --task TASK_ID --assignment ASSIGNMENT_ID \
  --disposition incorporated --evidence "reviewed diff and accepted result"
~~~

Если для задания нужны незакоммиченные изменения, импортируйте только необходимые файлы:

~~~bash
deepseek-team workspace import WORKSPACE_ID --include path/to/needed.py
~~~

Импортированные файлы учитываются как исходные материалы, подготовленные координатором. Они не засчитываются как работа воркера. Указанные в плане зависимости проверяются **внутри изолированного окружения воркера, до чтения API-ключа**. Для `full-access` недостаточно, чтобы JDK, SDK или другие инструменты были установлены только в основной системе. Подготовьте недостающие зависимости через `workspace prepare`. Проверка с заглушками вместо настоящих зависимостей не считается равноценной.

Если координатором выступает Claude Code, в приведённой выше команде запуска воркера укажите `--runtime claude` вместо `--runtime codex`.

Оба координатора могут использовать собственных субагентов при наличии обоснования. Эти субагенты работают с моделью, разрешениями и изоляцией среды своего координатора, вне изолированного окружения воркеров DeepSeek.

Профили 25/50/75 задают **целевое распределение работы, а не измеренный процент продуктивности**. DeepSeek Team записывает факты выполнения, но не рассчитывает «фактическую долю вклада» по количеству вызовов, файлов, строк, токенов, пунктов задачи или субъективной оценке результатов.

## Интеграция с проектом

`init` добавляет и обновляет один блок инструкций с маркерами границ в файле нужного координатора:

- Codex: `AGENTS.md`
- Claude Code: `CLAUDE.md`
- `--coordinator both`: оба файла

Содержимое за пределами этого блока и права доступа к файлу сохраняются. Инструкции требуют изоляции на уровне ОС и прямо запрещают координатору добавлять `--os-sandbox off`. Если изоляция не работает, нужно исправить её настройку или выполнить задачу силами координатора. При профилях 50/75 с доступом `full-access` независимые части реализации нужно делегировать **до** того, как координатор начнёт выполнять ту же работу сам. Архитектура, итоговая проверка и интеграция остаются за координатором.

При изменении настроек проекта пакет обновляет свои блоки инструкций, если они уже есть в файлах. Остальной пользовательский текст сохраняется. Инструкции по-прежнему требуют проверять действующие настройки перед каждым новым заданием.

Начиная с версии **0.5.0**, при обычном обновлении пакета **не нужно повторно запускать `init`** в подключённых проектах. Установщик и команда `setup` обновляют пользовательские хуки Codex, а существующий блок инструкций в проекте служит признаком того, что проект подключён. Запускайте `init`, когда подключаете новый репозиторий, добавляете второго координатора или восстанавливаете блок инструкций после `detach`.

## Делегирование в режиме `read-only`

Codex:

~~~bash
deepseek-team worker --runtime codex <<'TASK'
Inspect src/parser.py and tests/test_parser.py.
Find the cause of the empty-input failure. Do not implement changes.
Return concise evidence, suggested fix, risks and tests.
TASK
~~~

Claude Code:

~~~bash
deepseek-team worker --runtime claude <<'TASK'
Inspect src/parser.py and tests/test_parser.py.
Find the cause of the empty-input failure. Do not implement changes.
Return concise evidence, suggested fix, risks and tests.
TASK
~~~

`--runtime auto` выбирает Codex, если доступны оба CLI, и Claude Code — если доступен только он. В инструкциях, которые добавляет пакет, CLI всегда указан явно, чтобы выбор не менялся незаметно для координатора.

## Разработка в режиме `full-access`

Если действует режим `full-access`, команда `deepseek-team worker` создаёт изолированную рабочую копию из **коммита HEAD** исходного репозитория. Вместо новой копии можно указать уже существующую, созданную пакетом. Воркер может создавать, изменять и удалять файлы проекта, даже если они не были заранее перечислены в задании. Он также может запускать локальные тесты и сборки с зависимостями, подготовленными в этой копии.

Исходная рабочая копия пользователя не очищается и не передаётся под управление пакета. Незакоммиченные изменения, неотслеживаемые файлы и файлы, исключённые через `.gitignore`, остаются на месте и **не переносятся к воркеру автоматически**. Если они нужны для задания, координатор должен явно передать необходимые материалы, проверив, что это безопасно. Просить пользователя очистить рабочую копию для этого не нужно.

Пример разового запуска:

~~~bash
deepseek-team worker --runtime claude --delegation-level 50 --access full-access <<'TASK'
Implement the bounded parser fix.
Acceptance criteria:
- preserve the public parser API;
- add a regression test for empty input;
- run the focused local tests;
- report changed files and checks actually run.
TASK
~~~

Если нужно заранее установить зависимости или выполнить несколько заданий подряд в одной копии, создайте её отдельно и используйте её идентификатор:

~~~bash
deepseek-team workspace create /path/to/project
# Сохраните выведенный идентификатор рабочей копии

deepseek-team workspace prepare WORKSPACE_ID -- python3 -m venv .venv
deepseek-team workspace prepare WORKSPACE_ID -- .venv/bin/pip install -r requirements.txt

deepseek-team worker --runtime codex --workspace WORKSPACE_ID --access full-access <<'TASK'
Implement the assigned change and run the relevant local tests.
TASK

deepseek-team workspace diff WORKSPACE_ID
~~~

После успешного задания рабочую копию можно использовать повторно. Если воркер завершился с ошибкой, успев изменить файлы, сами файлы и список изменений сохраняются. Повторный запуск **не происходит автоматически**. Сначала проверьте рабочую копию, затем явно продолжите работу с `--resume-after-failure --workspace WORKSPACE_ID`.

Одновременно могут работать до трёх воркеров. Каждое задание в режиме `full-access` выполняется в отдельной копии с собственной блокировкой. Воркеры не видят копии друг друга и исходную рабочую копию пользователя. Итоговая проверка, интеграция, коммиты, отправка в удалённый репозиторий и развёртывание остаются за координатором.

## Управление изоляцией

~~~bash
deepseek-team sandbox status
deepseek-team sandbox install-apparmor
deepseek-team sandbox remove-apparmor
~~~

`install-apparmor` не перезаписывает `/etc/apparmor.d/deepseek-team-bwrap`, если его содержимое отличается от профиля в пакете, путь является символической ссылкой или указывает не на обычный файл. `remove-apparmor` удаляет профиль, только если его содержимое в точности совпадает с версией из пакета. Изменения администратора сохраняются.

Для диагностики предусмотрен запуск без изоляции на уровне ОС:

~~~bash
deepseek-team worker --os-sandbox off ...
~~~

Эта команда выводит предупреждение и отключает обязательную изоляцию на уровне ОС. Инструкции проекта, добавляемые пакетом, **не допускают её использования**. Она не предназначена для обхода ошибок изоляции в рабочей среде.

## Надёжность и границы безопасности

- Общие блокировки на уровне пользователя ограничивают число одновременно работающих воркеров тремя. Для рабочих копий дополнительно проверяется исключительное право на использование.
- Общее время выполнения по умолчанию не ограничено: тайм-аут равен `0`. Если воркер долго работает или не выводит сообщений, это само по себе не считается сбоем.
- При временных сбоях в режиме `read-only` возможны повторные попытки в пределах заданного лимита. В режиме `full-access` предусмотрена одна попытка: частичный результат сохраняется, а для продолжения нужен явный параметр `--resume-after-failure`.
- Воркер должен вернуть полный результат в заданном формате. Некорректный JSON, недопустимые последовательности UTF-8, сообщения об окончательном сбое и пустые ответы со статусом успеха отклоняются.
- `DEEPSEEK_TEAM_DISABLED=1` отключает делегирование. Прежняя переменная `CODEX_DEEPSEEK_DISABLED=1` поддерживается для совместимости.
- Название модели в задании отражает запрос, но не доказывает, какая модель на сервере его выполнила. Команда `doctor --live` проверяет подключение к нужному провайдеру в пределах доступных возможностей.

Bubblewrap и AppArmor значительно усиливают изоляцию, но DeepSeek Team **не гарантирует защиту конфиденциальных данных от любого вредоносного репозитория или исполняемого файла координатора**. Изолированному окружению Claude доступны рабочее дерево и файлы, необходимые для запуска CLI. Codex использует собственные правила изоляции на основе Bubblewrap. Если секреты хранятся прямо в репозитории, модель может прочитать их как обычные файлы проекта. Для более строгой изоляции используйте отдельного пользователя ОС, контейнер или виртуальную машину.

~~~bash

deepseek-team config show --effective
deepseek-team doctor --runtime codex --offline

deepseek-team doctor --runtime both --offline

# Проверить возможности режима full-access для выбранных настроек
deepseek-team doctor --runtime both --offline --delegation-level 50 --access auto

PYTHONPATH=src python3 -m unittest discover -s tests -v
~~~

`doctor --offline` проверяет локальную изоляцию и возможности CLI, показывает наличие хуков и подключение проекта для выбранного координатора. Команда не обращается к API DeepSeek и не проверяет действительность ключа. Она также не подтверждает, что текущая сессия включила хуки. `doctor --live` выполняет платные запросы к DeepSeek: создаёт тестовый репозиторий и проверяет, что выбранные воркеры в режиме `read-only` его не изменяют.

Локальные тесты используют подставные ключи и имитацию обмена с API. GitHub Actions запускает полный набор тестов `unittest`, собирает и устанавливает wheel-пакет, проверяет оба имени консольной команды на Python 3.11, 3.12 и 3.13. Отдельное задание для Ubuntu проверяет Bubblewrap и AppArmor.

Процесс CI **Delegation verification** устанавливает конкретные зафиксированные версии Codex и Claude и проверяет их настоящие инструменты и протоколы через локальный имитатор API. Проверки охватывают запрет записи в `read-only`, создание файлов, не перечисленных заранее, и запуск локальных тестов в `full-access`, параллельную работу в изолированных копиях, явное продолжение после сбоя и различение ошибок провайдера и ошибок выполнения. Настоящий ключ DeepSeek и платные запросы для этого не нужны. Поэтому успешное прохождение CI само по себе не подтверждает работу с реальной моделью DeepSeek.

## Обновление и удаление

Если пакет установлен из клонированного репозитория через `install.py`, обновите его так:

~~~bash
git pull --ff-only
python3 install.py --with-sandbox   # рекомендуется в Ubuntu
deepseek-team hooks status --runtime auto
deepseek-team doctor --runtime auto --offline
~~~

Если проект уже подключён, повторный запуск `init` после обновления **не нужен**. Новый репозиторий подключается один раз командой `deepseek-team init --coordinator codex /path/to/project`. Если нужны инструкции для обоих координаторов, укажите `--coordinator both`. В Codex откройте `/hooks`, проверьте хук DeepSeek Team и подтвердите доверие к нему.

Если вы используете pipx, выполните `pipx upgrade codex-deepseek-team`, затем `deepseek-team hooks install --runtime auto`, `deepseek-team hooks status --runtime auto` и `deepseek-team sandbox status`.

Чтобы убрать из проекта инструкции DeepSeek Team и удалить настройки координаторов, добавленные пакетом:

~~~bash
deepseek-team detach --coordinator both /path/to/project
deepseek-team reset --runtime both
deepseek-team auth remove       # необязательно
~~~

При необходимости удалите и профиль AppArmor. Команда удалит его только в том случае, если он не был изменён:

~~~bash
deepseek-team sandbox remove-apparmor
~~~

`reset --runtime codex` удаляет неизменённый блок настроек провайдера DeepSeek и хуки Codex, добавленные пакетом. `reset --runtime claude` удаляет только обработчики DeepSeek Team из настроек Claude. Основная модель, данные входа, разрешения и чужие настройки сохраняются в обоих случаях. Ключи в переменных окружения и приватные резервные копии конфигурации Codex также сохраняются.

После отключения проектов удалите Python-пакет через менеджер пакетов, которым его устанавливали. Если использовали установщик, можно вручную удалить созданные им символические ссылки `~/.local/bin/deepseek-team` и `~/.local/bin/codex-deepseek-team`, а также каталог `~/.local/share/codex-deepseek-team`.

## Поддерживаемые платформы

Текущая версия работает **только в Linux**. Поддержка Windows отложена: для неё сначала нужно обеспечить такой же уровень изоляции воркеров.
