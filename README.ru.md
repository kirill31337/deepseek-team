**Субагенты DeepSeek Flash внутри вашей сессии Codex или Claude Code.**

<a id="возможности"></a>

Передавайте реализацию, тесты и документацию воркерам DeepSeek из привычной сессии Codex или Claude Code. Координатор заранее распределяет работу, проверяет изменения по согласованным критериям и переносит принятые результаты в основной проект.

Координатор оценивает качество работы воркера отдельно от проблем в задании, контексте или окружении. Приватный журнал разборов помогает точнее ставить следующие задачи.

```bash
pipx install deepseek-team
```

Для установки нужны Linux, Python 3.11+ и [pipx](https://pipx.pypa.io/latest/how-to/install-pipx.html). После установки [сохраните API-ключ, настройте хуки и подключите проект](#подготовка-и-подключение-проекта).

*Схема работы с включённым `full-access`.*

Этот README описывает ветку `main`. Устанавливайте последний выпущенный пакет из [PyPI](https://pypi.org/project/deepseek-team/), а заметки о версиях смотрите на странице [релизов](https://github.com/kirill31337/deepseek-team/releases/latest). Пакет устанавливает единственную команду `deepseek-team`.

Воркеры работают с моделью `deepseek-flash`, для них нужен отдельный **ключ DeepSeek API**. По умолчанию координатор выбирает глубину рассуждений (`low`, `high` или `max`) для каждого задания; можно сохранить и фиксированный уровень. `low` подходит для простых и механических задач, `high` — для обычной работы, `max` — для сложной отладки, анализа нескольких связанных файлов и тщательного независимого ревью. Если уровень не выбран, воркер использует `high`. Старое значение `medium` принимается как синоним `high`, поэтому прежние настройки и команды продолжают работать. Подробнее — в [руководстве DeepSeek по режиму размышлений](https://api-docs.deepseek.com/guides/thinking_mode/).

Сразу после установки воркерам разрешено **только чтение**: они изучают проект и сообщают о результатах. Чтобы разрешить им менять файлы в изолированных копиях разработки, явно включите `full-access`.

## Требования

- **Linux.** Поддержка Windows и macOS не заявлена.
- **Python 3.11 или новее** и **Git** в `PATH`.
- **Codex CLI и/или Claude Code CLI** в `PATH`, установленные и настроенные обычным способом. Установите нужного координатора; значение `both` готовит обоих.
- **Bubblewrap** (`bwrap`) и рабочая песочница Linux. Она нужна каждому воркеру до чтения учётных данных, и её нельзя отключить.

В Ubuntu команда `setup --with-sandbox` может установить необходимые системные компоненты (см. ниже). В других дистрибутивах сначала установите Bubblewrap и компоненты AppArmor своим менеджером пакетов, затем проверьте `deepseek-team sandbox status`.

## Установка и первый запуск

Пакет опубликован в [PyPI](https://pypi.org/project/deepseek-team/), поэтому установка выполняется по имени пакета. [pipx](https://pipx.pypa.io/latest/how-to/install-pipx.html) держит CLI в отдельном окружении и остаётся рекомендуемым способом:

```bash
sudo apt-get install pipx      # Ubuntu, один раз
pipx ensurepath
# Затем откройте новый терминал, чтобы обновился PATH.
pipx install deepseek-team
```

Другие менеджеры, если вы уже предпочитаете их:

```bash
# uv
uv tool install deepseek-team

# pip только внутри виртуального окружения
python3 -m venv ~/venvs/deepseek-team
. ~/venvs/deepseek-team/bin/activate
python -m pip install deepseek-team
```

Установка из локальной копии репозитория:

```bash
git clone https://github.com/kirill31337/deepseek-team.git
cd deepseek-team
pipx install .
```

### Подготовка и подключение проекта

`setup` настраивает интеграцию для вашего пользователя, а `init` подключает проект Git, в котором вы хотите делегировать задачи.

```bash
# 1. Готовит интеграцию для Codex. --no-key откладывает ввод ключа.
deepseek-team setup --runtime codex --no-key

# 2. Сохраняет ключ DeepSeek API. Ввод скрыт, ключ нигде не отображается.
deepseek-team auth set

# 3. Подключает проект, чтобы координатор читал инструкции по делегированию.
cd /path/to/project
deepseek-team init --coordinator codex .

# 4. Необязательно: разрешает изменения в изолированной копии разработки.
deepseek-team config set --project --access full-access

# 5. Проверяет локальную готовность. Команда работает офлайн: ключ не читается, запросы не отправляются.
deepseek-team doctor --runtime codex --offline
```

Несколько пояснений:

- `--no-key` намеренно откладывает авторизацию, чтобы `setup` не запрашивал и не читал секрет. Сохраните ключ отдельно командой `deepseek-team auth set` или не указывайте `--no-key`, когда готовы ввести его сразу.
- При первой установке доступ — **read-only**. Шаг 4 разрешает Auto делегировать реализацию, явно выдавая право записи. `full-access` означает отдельную приватную копию разработки, а не доступ к системе. В конце `setup` выводит эту подсказку и команду явного включения, но сам ничего не меняет.
- В Ubuntu для первой настройки может понадобиться `deepseek-team setup --runtime codex --with-sandbox --no-key`: параметр `--with-sandbox` разрешает установить пакет песочницы и именованный профиль AppArmor. Обычный `setup` не вызывает `sudo`; в других дистрибутивах установите системные компоненты заранее.
- Для Claude Code замените `codex` на `claude` в параметрах `--runtime` и `--coordinator` или укажите `both` для обоих координаторов.
- Хуки — обработчики событий сессии, через которые DeepSeek Team подключается к координатору. В Codex откройте `/hooks`, проверьте установленный хук и подтвердите доверие; в Claude Code начните новую сессию и проверьте `/hooks`. Пакет не может подтвердить доверие к хукам за вас, а после обновления начните новую сессию, чтобы загрузились обновлённые инструкции.
- Подключённые проекты хранят собственные управляемые блоки: при старте сессии и при вводе запроса явно подключённый проект проверяет и при необходимости обновляет оба существующих блока в `AGENTS.md` и `CLAUDE.md` по текущему шаблону пакета и действующим настройкам. В неподключённых проектах файлы не создаются, не сканируются и не регистрируются.
- Для каждого координатора можно включить сокращённый **linked**-бутстрап, разместив
  маркер `guidance:linked` на отдельной строке **внутри** существующего управляемого блока,
  с тем же префиксом комментария, что и у маркера `managed-block:start` этого блока. Разместите
  его после существующего служебного комментария `original:...`; первые две строки блока
  оставьте без изменений. Маркер
  вне управляемого блока — в вашем тексте или в примере кода — не действует. После этого
  пакет создаёт компактный (менее 4 КБ) блок, который обязывает прочитать поддерживаемый
  вручную `docs/agents/delegation.md` в корне репозитория и указывает на актуальные команды
  `deepseek-team status` и `config show --effective --instructions --runtime codex|claude`
  вместо встраивания снимка действующего профиля.
- Прежде чем включать режим в проекте, обновитесь до 0.8.8 или новее и создайте в корне
  репозитория непустой обычный файл `docs/agents/delegation.md` в кодировке UTF-8, который
  содержит собственно требуемый протокол делегирования, а не пустую заглушку, и держите его
  под контролем версий. Пакет проверяет этот гид, но никогда не создаёт и не обновляет его
  содержимое, поэтому гид остаётся обязанностью человека и при последующих обновлениях. Если
  гид отсутствует, пуст, не в UTF-8, является символической ссылкой или выходит за пределы
  репозитория, включение режима завершается ошибкой, а управляемые файлы не меняются.
- Запустите `init`, чтобы намеренно пересобрать блок этого проекта. После этого маркер
  переживает `init`, обновление конфигурации и автоматическое обновление сессии, поэтому
  выбранный режим сохраняется, пока вы не удалите маркер, а `detach` работает в обоих
  режимах. Проекты без маркера остаются в режиме полного блока по умолчанию.
  Точный маркер приведён в [заметках к версии 0.8.8](https://github.com/kirill31337/deepseek-team/blob/main/docs/releases/0.8.8.md#русский).

## Делегирование и текущие настройки

### Что делегируется

Auto передаёт подходящие задачи сразу и не ждёт накопления истории. Задача хорошо подходит, если она:

- небольшая или средняя, с низким или средним риском;
- локализована в известном или частично известном месте, со связями в пределах участка или компонента;
- имеет ясные критерии приёмки и способ проверки.

Для реализации нужна запускаемая проверка — тесты, сборка или воспроизведение ошибки; для ревью, исследования и документации достаточно ручных критериев. Неизвестная стоимость не мешает передать задачу, а отсутствие или неполнота истории качества не блокирует подходящую работу. Если измеренные затраты не оправдывают делегирование или по классу задач накопилась достаточно подтверждённая плохая история качества, задача остаётся у координатора; по мере старения данных допуск возобновляется.

Каждую делегированную подзадачу — даже небольшой поиск или ревью — планируют и маршрутизируют до назначения другого агента; в режиме Auto решение о воркере означает DeepSeek. Собственные субагенты координатора — явное исключение: нужны записанная причина и либо нативная возможность, недоступная воркеру DeepSeek, либо явная просьба пользователя.

Неизвестный параметр задачи остаётся неизвестным: координатор регистрирует ограниченную диагностическую задачу вместо заявления о безопасной реализации и объединяет независимые подходящие области в один план до того, как дублировать эту работу.

### Как работает маршрутизация

Координатор описывает задачу до её выполнения. Это описание используется при выборе исполнителя, оценке качества и проверке результата:

- **Классификатор — координатор, до запуска.** Координатор описывает задачу в *карточке признаков*: вид, предметная область, операция, локализация, связность, риск, объём, ясность и способ проверки. Неуказанные признаки остаются `unknown`, их не угадывают. Архитектура, безопасность, интеграция, итоговая проверка, работа с секретами, подписание и публикация остаются у координатора.
- **Допуск и маршрутизатор.** Допуск проверяет критерии задачи, права доступа, паузу, измеренные затраты и накопленную локальную оценку качества, после чего маршрутизатор выбирает воркера или координатора в этих границах. Auto сразу допускает подходящую ограниченную работу, а права доступа никогда не расширяются автоматически.
- **Оценщик.** По сопоставимым записанным случаям он строит оценку качества по рубрике с интервалом неопределённости. Это описательная оценка по реальным случаям, а не калиброванная вероятность успеха на вашем коде, и она не задаёт универсальную долю делегирования.
- **Проверяющий и обратная связь.** После проверки реального diff и заявленных проверок координатор отдельно записывает наблюдаемый исход и *оценённое качество* работы воркера: `met`, `minor_gaps`, `major_gaps`, `unusable` или нейтральное `unassessable` с атрибуцией `worker`, `shared`, `coordinator`, `environment` или `unknown`. Пробел в брифе, контексте или изменившиеся требования сами по себе не снижают качество работы воркера, а к паузе класса задач ведут только `major_gaps` или `unusable` с атрибуцией `worker`/`shared`.

### Обратная связь и уроки

Записанные исходы, включая чистые успехи, попадают в приватный журнал уроков проекта в режиме append-only, который хранится вне Git. Координатор разбирает его, когда это положено: после 10 новых или обновлённых проверенных случаев либо после 3 различных случаев доработки с одним видом задачи и известной причиной. По итогам разбора он может применить ограниченные, версионированные и рекомендательные правила, которые делают следующие брифы точнее; разбор может явно ничего не менять. Модели не обучаются и не запускаются в фоне, а публичные результаты бенчмарков используются только при явном импорте — автоматически они не собираются и не поставляются в комплекте.

Локальное состояние можно посмотреть, ничего не меняя:

```bash
deepseek-team routing status --path PROJECT --json
deepseek-team routing stats --path PROJECT           # качество по категориям; --json — полные счётчики
deepseek-team lessons status --path PROJECT --json
deepseek-team lessons review --path PROJECT --json  # только набор для разбора; ничего не применяется
```

`routing stats` только читает и группирует записанные исходы воркеров по категориям задач; `lessons review --json` лишь печатает набор для разбора, с которым работает координатор. Полные правила и структуру данных описывают [руководство по выбору исполнителя](https://github.com/kirill31337/deepseek-team/blob/main/docs/ROUTING.ru.md) и [руководство по журналу доработок](https://github.com/kirill31337/deepseek-team/blob/main/docs/DELEGATION_LESSONS.ru.md).

### Права доступа

Права не зависят от `effort` и истории:

- **`read-only`** (по умолчанию после установки) — воркер изучает проект и сообщает о результатах, но не может его изменить.
- **`full-access`** (включается явно) — воркер реализует изменения, запускает локальные проверки и пишет документацию только в изолированной копии, принадлежащей заданию. Доступа ко всем ресурсам хоста этот режим не даёт.

Воркеры никогда не делают коммитов, не выполняют push, не публикуют и не развёртывают изменения, не обращаются к боевым сервисам и не запускают других агентов. Это задачи координатора.

### Ключевые параметры

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| Делегирование | `auto` | Выбирает исполнителя под задачу; фиксированной квоты нет |
| Права доступа | `auto` -> `read-only` в Auto | `full-access` включает изолированную реализацию |
| Модель | `deepseek-flash` | Фиксирована для всех воркеров |
| `effort` | `auto` | Координатор выбирает `low`/`high`/`max`; `medium` — синоним `high` |
| Воркеры | `8` | Настраивается от 1 до 64; лишние задачи ждут в очереди FIFO |
| Общий таймаут | без ограничения | Явный таймаут включает время в очереди |

Просмотр и изменение настроек проекта:

```bash
deepseek-team config show --effective
deepseek-team config set --project --max-workers 8
deepseek-team on      # включить делегирование в проекте
deepseek-team off     # выключить, не удаляя настройки
deepseek-team status  # сохранённое и действующее состояние
```

Вместо Auto можно выбрать ручной профиль **25/50/75**: он задаёт желаемое распределение работы между координатором и DeepSeek. Эти профили не являются измеренными квотами. Сохранённый ручной профиль имеет приоритет над Auto, а записанные результаты продолжают использоваться для обучения. При `access=auto` профиль 25 использует `read-only`, а профили 50/75 — `full-access`. Явно сохранённый `read-only` всегда имеет приоритет. Подробнее — в [руководстве по выбору исполнителя](https://github.com/kirill31337/deepseek-team/blob/main/docs/ROUTING.ru.md).

Пакет поставляет правила делегирования и управляемые блоки. В каждом проекте остаются свои права доступа, ручной профиль, `effort`, `max_workers` и состояние `off`, а приватный журнал уроков хранится локально: новая версия обновляет правила работы, но не меняет сохранённые настройки, не экспортирует `full-access` или выученные правила и не обещает одинаковую долю делегирования.

## Пример задания координатору

Когда установка и подключение готовы, воркеров не запускают вручную. Опишите задачу в обычной сессии координатора простыми словами:

> Реализуй новый слой кэша в `src/cache/`. Передай независимые части реализации и тесты воркерам DeepSeek, запусти тесты внутри копий воркеров и перенеси в проект только то, что проверил. Публичный API не меняй и покажи итоговый diff до коммита.

Координатор разделит задачу на ограниченные задания, проведёт их через очередь воркеров и отчитается о принятой работе.

В пакет входят инструкции по итоговому отчёту для Codex и Claude Code. Когда DeepSeek Team включён, координатор кратко перечисляет, что сделал лично, какие результаты DeepSeek принял и что потребовало доработки, было отклонено или завершилось с ошибкой, а затем приводит приблизительное соотношение своего вклада и вклада DeepSeek в **принятую работу**: два целых процента с суммой 100 и пометкой **«субъективная оценка, не измерение»**. Оценка учитывает объём и сложность принятой работы, проверку и доработки; её нельзя вычислять по числу вызовов, задач, файлов, строк, токенов или затраченному времени, и она не служит обратной связью для маршрутизатора. Старт сессии добавляет текущую политику для Codex и Claude Code; если обновлённый блок изменился или обновление не удалось, следующий запрос выдаёт свежие указания, чтобы устаревшая загруженная версия не сохранялась. Обновление пакета обновляет инструкции для хуков, каждый подключённый проект обновляет свои блоки при следующей сессии или запросе, а `setup` обновляет блоки в своём текущем репозитории. Запускайте `init` только для первого подключения проекта или намеренного восстановления его блоков.

## Полезные команды

Диагностика:

```bash
deepseek-team doctor --runtime codex --offline   # локальные проверки, без сети
deepseek-team hooks status --runtime codex       # установлены ли управляемые хуки
deepseek-team sandbox status                     # Bubblewrap и профиль AppArmor
deepseek-team auth status                        # только наличие сохранённого ключа
```

Эти команды не обращаются к провайдеру. Локальная проверка не подтверждает ключ в DeepSeek; реальные запросы воркеров идут через вашу учётную запись DeepSeek API.

## Изоляция

<a id="гигиена-рабочих-копий-и-веток"></a>

Воркеры работают только в песочнице Linux с Bubblewrap. Задания с правом записи выполняются в отдельной копии разработки с ограниченным доступом к файловой системе и сети. Для режимов чтения и записи действуют разные ограничения файловой системы, учётных данных и сети, а копии воркеров не удаляются автоматически. За архитектуру, решения по безопасности, итоговую проверку и интеграцию отвечает координатор. Точные правила — в [руководстве по изоляции](https://github.com/kirill31337/deepseek-team/blob/main/docs/HARDENING.ru.md).

<a id="предварительная-проверка-источника-и-восстановление"></a>

Перед созданием копии координатор может выполнить необязательную проверку закоммиченного источника: `deepseek-team workspace check --json` читает только имена и режимы файлов из `HEAD`, не вызывает модель, не создаёт копию и завершается кодом `0`, если источник подходит, или `78` при блокировке. Неудачное задание сохраняет свою копию для осмотра командой `deepseek-team workspace show WORKSPACE_ID`; продолжение остаётся явным, автоматической очистки не существует. Полные правила проверки и восстановления — в [руководстве по изоляции](https://github.com/kirill31337/deepseek-team/blob/main/docs/HARDENING.ru.md).

## Подготовка инструментов и повторная проверка

Воркеры видят только собственную копию, нужные каталоги среды выполнения и временный домашний каталог внутри разреженного пространства имён — но не корень хост-системы, ваш домашний каталог или установленные SDK. Поэтому лаунчер, работающий в вашей оболочке, может не запуститься внутри пространства имён воркера, если соседний файл не смонтирован. Подготовка копирует явно выбранный набор инструментов в собственную копию, чтобы он действительно был там виден, а объявленные smoke-проверки определяют готовность до чтения ключа провайдера.

```bash
# Декларативная подготовка: скопировать JDK только для чтения и объявить проверку.
deepseek-team workspace prepare WORKSPACE_ID \
  --tool JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 \
  --env 'JAVA_HOME={workspace}/.deepseek-tools/JAVA_HOME' \
  --env 'PATH={workspace}/.deepseek-tools/JAVA_HOME/bin' \
  --probe 'java -version' \
  --save-project

# Повторить объявленные проверки, не тратя новый запрос к модели.
deepseek-team workspace verify WORKSPACE_ID --check 'java -version' --timeout 120
```

- `--tool NAME=HOST_DIR` копирует выбранный каталог программного обеспечения в `.deepseek-tools/NAME`, доступный внутри пространства имён только для чтения. `--copy SOURCE=REL_DEST` копирует явные несекретные файлы или кэши; кэши остаются доступными для записи в копии. `--env NAME=VALUE` принимает только `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `GRADLE_USER_HOME`, `M2_HOME`, `KOTLIN_HOME` и `PATH`, каждый с корнем в рабочей копии через литерал `{workspace}`.
- `--probe COMMAND` выполняется только внутри пространства имён воркера, до обращения к ключу модели; неудачная проверка останавливает задание. `--save-project` сохраняет приватный рецепт, который воспроизводит эти объявления в последующей копии и никогда не выполняет и не воспроизводит команды хост-системы. Прежняя форма `workspace prepare ID -- COMMAND ARG ...` не меняется и по-прежнему выполняется на хост-системе координатора.
- `workspace verify ID [--check COMMAND] [--timeout SECONDS] [--json]` заново собирает подготовленную среду, повторяет объявленные или заданные проверки и добавляет свидетельства. Команда никогда не читает ключ провайдера, не запускает релей и модель и сохраняет исходный результат воркера. Вывод ограничен 65 536 байтами на поток, редактируется и хранится только для владельца в приватном каталоге `diagnostics/` рабочей копии.
- Проверки снимаются как базовая линия до запуска модели, поэтому уже красный набор не блокирует задание на исправление. Неудачная проверка проекта остаётся нейтральной (`unknown`), пока координатор не изучит фактический diff и свидетельства.

Реалистичные рецепты для Java, Android и Gradle, правила материализации Java и безопасности, а также причины свидетельств описаны в [гиде по инструментам](https://github.com/kirill31337/deepseek-team/blob/main/docs/TOOLCHAINS.ru.md).

## Обновление и удаление

Обновление выполняется через тот же менеджер пакетов, после чего выполните `setup` один раз для каждого установленного координатора:

```bash
pipx upgrade deepseek-team
deepseek-team setup --runtime codex --no-key   # либо claude / both
deepseek-team doctor --runtime codex --offline
```

Обновление с 0.8.7 или 0.8.8 выполняется так же. `setup` обновляет пользовательские хуки выбранных координаторов и обновляет существующие управляемые блоки в файлах инструкций (`AGENTS.md` и `CLAUDE.md`) в том репозитории, откуда он запущен, если они уже подключены. Остальные подключённые проекты обновляют свои блоки автоматически при следующей сессии или запросе, поэтому повторять `init` в каждом существующем проекте больше не нужно; запускайте `init` только для первого подключения проекта или намеренного восстановления управляемых блоков. Перезаписываются только блоки, которыми владеет пакет, поэтому ваш текст и сохранённые настройки остаются на месте. Установка и обновление через pip, pipx или uv не запускают настройку автоматически. Команда `setup` обновляет определения хуков; доверие к ним подтверждается отдельно в координаторе. Закрытый проект обновит инструкции при следующем открытии. Для установки через uv используйте `uv tool upgrade deepseek-team`; для venv — `python -m pip install --upgrade deepseek-team` из этого окружения. Не устанавливайте пакет одновременно несколькими способами. Если он установлен через pipx из локального клона, обновите клон и выполните в нём `pipx install --force .`.

Сначала выполните `detach` для подключённых проектов, затем `reset`, чтобы удалить интеграцию DeepSeek Team с координатором, и только после этого удаляйте пакет. Команда `reset` сохраняет ваши основные настройки, выбранную конфигурацию и ключ DeepSeek. Если нужно удалить и сохранённый ключ, выполните `deepseek-team auth remove` до удаления пакета.

```bash
deepseek-team detach --coordinator codex /path/to/project   # для подключённых проектов
deepseek-team reset --runtime codex                         # удаляет интеграцию пакета
pipx uninstall deepseek-team
```

Сохранённые ключи при удалении пакета **не** удаляются. Для установки через uv используйте `uv tool uninstall deepseek-team`; для venv — `python -m pip uninstall deepseek-team` из этого окружения. В командах для Claude Code замените `codex` на `claude`; для обоих координаторов укажите `both`.
